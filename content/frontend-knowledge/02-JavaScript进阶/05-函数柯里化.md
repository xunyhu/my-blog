# 函数柯里化

## 一、是什么

柯里化（currying）是把一个接受多个参数的函数，改造成**依次接收单个参数、每次返回新函数**的等价形式：

```ts
// 原始：一次喂 3 个参数
const add3 = (a: number, b: number, c: number): number => a + b;

// 柯里化后：一次只喂 1 个，中间态仍是函数
const curriedAdd3 = curry(add3);
curriedAdd3(1)(2)(3); // 6
```

它不是「语法糖」，而是一次**函数形态的等价变换**。在类型论里这对应同构：

```text
f : (A × B × C) → R     原始形态：一次接收一个元组
f : A → (B → (C → R))   柯里化形态：返回"函数的函数"
```

两种形态携带的信息量完全相同，差别在于**参数到达的时间点被拆开**了。这个拆分正是全部工程价值的来源。

三个容易混进同一个词的东西，边界必须先划清：

| 变换     | 输入         | 输出                 | 关键差异               |
| -------- | ------------ | -------------------- | ---------------------- |
| 柯里化   | `(a,b,c)=>R` | `a=>b=>c=>R`         | 一次只吃 **1 个** 参数 |
| 偏应用   | `(a,b,c)=>R` | `(b,c)=>R`（固定 a） | 一次固定 **若干个**    |
| 函数组合 | `f,g`        | `x=>g(f(x))`         | 不改变 arity，只串联   |

`fn.length`（arity）在这里是决定性的输入。JS 的 `Function.prototype.length` 只统计**遇到第一个默认值或 rest 参数之前的形参个数**，这一点会直接坑住「用 `fn.length` 推断 arity」的实现（见第五节）。

## 二、为什么

前端手写题爱考柯里化，但真实项目里它的价值不在「`curried(1)(2)(3)` 很酷」，而在下面四件事。

**1. 参数复用：把「稳定部分」提取成配置对象之外的第三选择。**
一个日志函数 `fmt(level, scope, msg)` 在告警代码里 90% 的调用都是 `level='warn'`。柯里化后 `const warnLog = curriedFmt('warn')`，调用点只关心真正变化的东西。这比传默认值更精确：默认值把「缺省」和「有意传空」混为一谈。

**2. 延迟执行：把「决定做什么」和「什么时候做」解耦。**
`fetchWith(baseURL, headers)` 在模块初始化时就能定型的请求描述，等到用户交互时再补最后的路径与 body。柯里化天然提供了这种「先填一半、等时机到了再填另一半」的容器。

**3. 让函数可以组合。**
`compose`/`pipe` 要求每个环节是**单元函数**（一进一出）。一个 `(a,b)=>c` 的函数塞不进管道，柯里化后 `a=>(b=>c)` 只喂第一个参数，剩下的部分作为一个函数继续参与组合。这是柯里化在函数式风格里存在的结构性理由。

**4. 生成更专化的函数（specialization）。**
`const isValidEmail = matches(emailPattern)`、`const ceilTo10 = ceilTo(10)`：把通用函数变成命名清晰的专用函数，调用点从「读参数才知道意图」变成「读函数名就知道意图」。

代价同样明确：多一层闭包分配、调用栈变深、调试时断点位置不直观、TS 签名复杂度上升。**柯里化应该发生在「预设一次、执行多次」的边界上**，而不是每个三参数函数都包一遍。

## 三、核心原理

### 参数收集的过程

```text
curry(add3)  arity = add3.length = 3

调用链                      已收集参数           判断                 返回
curry(add3)                 []                   0 < 3                函数
      (1)                   [1]                  1 < 3                函数
      (2)                   [1,2]                2 < 3                函数
      (3)                   [1,2,3]              3 >= 3  → add3(1,2,3) 6
```

实现要点只有两条：**用一个数组累积参数**、**用 arity 决定何时真正调用**。下面是我实际跑通的实现（Node 22.14 验证）：

```ts
// 运行时核心：received 是普通数组参数，不是 rest 参数
function curryN<TArgs extends readonly unknown[], TResult>(
  fn: (...args: TArgs) => TResult,
  arity: number,
): unknown {
  function step(received: unknown[]): unknown {
    if (received.length >= arity) {
      return fn(...(received as unknown as TArgs));
    }
    return (...next: unknown[]) => step([...received, ...next]);
  }
  return step([]);
}
```

写这段代码时踩过的坑值得记录：如果把 `step` 声明成 rest 参数 `(...received)`，那么 `step([])` 会让 `received` 变成 `[[]]`——长度永远是 1，参数被层层嵌套，函数永远不会触发。实测打印调用轨迹是 `step 收到 = [[]]` → `[[[],"x"]]` → `[[[[],"x"],"y"]]`，链子越收越长却不求值。**「数组参数」与「rest 参数」在递归收集场景下不可互换。**

### TypeScript 签名：严格单元链

```ts
export type Curried<
  TArgs extends readonly unknown[],
  TResult,
> = TArgs extends readonly [
  infer Head,
  ...infer Rest extends readonly unknown[],
]
  ? (arg: Head) => Curried<Rest, TResult>
  : TResult;

export function curry<TArgs extends readonly unknown[], TResult>(
  fn: (...args: TArgs) => TResult,
  arity: number = fn.length,
): Curried<TArgs, TResult> {
  return curryN(fn, arity) as Curried<TArgs, TResult>;
}

const curriedAdd3 = curry(add3);
curriedAdd3(1)(2)(3); // ✅ number
// @ts-expect-error 严格单元链不接受一次传两个参数
curriedAdd3(1, 2);
```

这个签名是**递归条件类型**：每次剥掉元组头一个元素，构造出 `(arg: Head) => ...`，直到元组空掉返回 `TResult`。它换来的收益是中间态类型精确——`curriedAdd3(1)(2)` 的类型是 `(arg: number) => number`，可以被继续传递、被别的函数消费。

如果想兼容 lodash 那种「一次可以喂多个参数」的风格，条件类型不再够用，需要**重载穷举**（`@types/lodash` 的做法）：

```ts
export interface Curry3<A, B, C, R> {
  (a: A): (b: B) => R;
  (a: A, b: B): (c: C) => R;
  (a: A, b: B, c: C): R;
}
```

运行时实现完全复用 `curryN(fn, 3)`，只是换一层类型包装。实测四种调用方式全部得到 `6`：`(1,2)(3)`、`(1)(2,3)`、`(1)(2)(3)`、`(1,2,3)`。重载数量随参数个数指数增长，这也是为什么 lodash 只提供 `curry` 的宽松语义而不承诺精确类型。

### arity 必须可覆盖

```ts
const withDefault = (a: number, b: number = 10): number => a + b;
withDefault.length; // 1 —— 默认值之后的参数不计入

curry(withDefault); // arity=1：喂一个参数就"求值"，返回 15
curry(withDefault, 2); // 显式 arity=2：forced(5)(100) → 105

const sumAll = (...nums: number[]): number => nums.reduce((s, n) => s + n, 0);
sumAll.length; // 0 —— curry(sumAll) 一调用就用 [] 求值，返回 0
```

结论：`fn.length` 只能当**默认猜测**，实现必须允许显式传入 arity。默认参数、rest 参数、可选参数三者都会让 `length` 与直觉不符。

### 与 partial / compose / pipe 的关系

```ts
export function partial<Head extends unknown[], Tail extends unknown[], R>(
  fn: (...args: [...Head, ...Tail]) => R,
  ...head: Head
): (...tail: Tail) => R {
  return (...tail) => fn(...(head as [...Head]), ...(tail as Tail));
}

export function compose2<A, B, C>(g: (b: B) => C, f: (a: A) => B): (a: A) => C {
  return (a) => g(f(a));
}

export function pipe<T>(...fns: Array<(value: T) => T>): (value: T) => T {
  return (value) => fns.reduce((acc, fn) => fn(acc), value);
}
```

三者关系可以一句话概括：**partial 是柯里化的「一次固定多个」变体，compose/pipe 是把单元函数串起来的胶水，而柯里化负责把多元函数变成能被这些胶水处理的形状。**

实测输出（同一次运行）：

```text
partial(fmt,'info')("network","retry 3")      → [info] network: retry 3
pipe(inc,double,inc)(3)                       → 9          // ((3+1)*2)+1
compose2(toText, pipe(inc,double))(3)         → n=8        // 右到左：先 pipe 再转字符串
```

中间件是 `compose` 的高阶变体（Koa/Redux 同源），也是很多人误当成「柯里化」的那个东西：

```ts
type Next = () => Promise<void>;
type Middleware = (ctx: Record<string, unknown>, next: Next) => Promise<void>;

export function composeMiddleware(
  middlewares: Middleware[],
): (ctx: Record<string, unknown>) => Promise<void> {
  return (ctx) => {
    const dispatch: Next = middlewares.reduceRight<Next>(
      (next, mw) => () => mw(ctx, next),
      () => Promise.resolve(),
    );
    return dispatch();
  };
}
```

实测洋葱顺序 `a-in > b-in > b-out > a-out`。这里没有任何柯里化：每个中间件本来就是 `(ctx, next)` 的多元函数，`reduceRight` 做的是**函数复合**，不是参数拆分。

### 与记忆化的组合

柯里化和 `memoize` 是天然搭配——预设参数后，缓存键的维度降低，命中率上升：

```ts
export function memoize<A extends unknown[], R>(
  fn: (...args: A) => R,
): (...args: A) => R {
  const cache = new Map<string, R>();
  return (...args: A): R => {
    const key = JSON.stringify(args);
    const hit = cache.get(key);
    if (hit !== undefined) return hit;
    const value = fn(...args);
    cache.set(key, value);
    return value;
  };
}

let calls = 0;
const slowAdd = (a: number, b: number, c: number): number => {
  calls += 1;
  return a + b + c;
};
const memoCurried = curry(memoize(slowAdd), 3);
```

实测 `memoCurried(1)(2)(3)` 两次 + `memoCurried(4)(5)(6)` 一次，得到 `6 6 15`，而 `calls === 2`。注意顺序：`curry(memoize(fn))` 缓存的是**完整参数组**；写成 `memoize(curry(fn))` 则缓存的是「返回中间函数」这个动作，命中后仍会执行原函数，属于典型误用。

## 四、工程实践

### 1. 日志与埋点：预设稳定维度

```ts
const fmt = (level: string, scope: string, msg: string): string =>
  `[${level}] ${scope}: ${msg}`;
const curriedFmt = curry(fmt);

const warnLog = curriedFmt('warn');
warnLog('network')('retry 3'); // [warn] network: retry 3
```

实测 `curriedFmt('warn')('auth')` 的类型是函数，值尚未求值——这正是「延迟到 msg 出现」的形态。真实项目里我会把这类预设写成**具名工厂**而不是裸柯里化链（`createLogger('warn', 'network')`），让栈追踪和 code search 都能命中名字。

### 2. 请求封装：预设放在模块边界，执行放在事件里

```ts
const request =
  (baseURL: string) => (headers: Record<string, string>) => (path: string) =>
    fetch(baseURL + path, { headers });

const callAPI = request('https://api.example.com')({ 'X-App': 'hurui.dev' });
// 组件里只剩 callAPI('/user/1')，baseURL 与鉴权头在初始化时定型一次
```

判断标准：**被预设的参数是否真的「进程生命周期内不变」**。如果它随用户登录态变化，柯里化会把它固化进闭包，变成 stale 值——这类参数应当作为最后一层参数在调用时读取。

### 3. 事件处理器工厂

```ts
const withPrevent = (handler: (e: Event) => void) => (e: Event) => {
  e.preventDefault();
  return handler(e);
};
const withStop = (handler: (e: Event) => void) => (e: Event) => {
  e.stopPropagation();
  return handler(e);
};
form.addEventListener('submit', withPrevent(submitHandler));
```

比 `handler.bind(null, ...)` 好的地方是保留了 `this` 语义与可读的意图命名；比每次写箭头函数好的地方是**逻辑只有一份**。

### 4. React：预设要放在渲染之外

```tsx
// ❌ 每次渲染都新建一层柯里化链，传给子组件的引用必然变化
const onClick = log('banner')('click');

// ✅ 预设一次，引用稳定
const logBannerClick = useMemo(() => log('banner')('click'), [log]);
```

配合 `useCallback` 使用同理：柯里化的中间态是**新函数对象**，凡是把它放进 props 或依赖数组的地方，都要考虑引用稳定性。React Compiler 能自动记忆化这类表达式，但它依赖的是可推断的纯表达式——把副作用藏进柯里化链会降低推断成功率。

### 5. 占位符：解决「只想预设第二个参数」

严格柯里化无法跳过第一个参数，Ramda 用占位符解决：

```ts
const hole = Symbol('curry.hole');
const __ = hole;

function curryHole<A, B, C, R>(fn: (a: A, b: B, c: C) => R) {
  function merge(received: unknown[], next: unknown[]): unknown[] {
    const merged: unknown[] = [];
    let i = 0;
    for (const slot of received) {
      merged.push(slot === hole && i < next.length ? next[i++] : slot);
    }
    while (i < next.length) merged.push(next[i++]);
    return merged;
  }
  function step(received: unknown[]): unknown {
    const full = received.length >= 3 && received.every((v) => v !== hole);
    if (full) return fn(received[0] as A, received[1] as B, received[2] as C);
    return (...next: unknown[]) => step(merge(received, next));
  }
  return (...args: unknown[]) => step(args);
}
```

实测 `gh(__,'mid')('x')('y')` 得到 `x|mid|y`，`gh('a')(__,'c')('b')` 得到 `a|b|c`。工程上我建议**不要**在生产代码引入占位符语义：它把「参数顺序」变成隐性契约，重构时极难被静态检查发现。想跳过第一参数，直接写偏应用或显式箭头函数。

### 6. 性能量级与选择判据

一次柯里化调用至少产生 1 个闭包 + 1 个新数组。在「预设一次、执行百万次」的场景这笔开销可忽略；在「每次调用都重新 curry」的热路径（如渲染循环、大数组 map）则是纯亏损。

经验判据（三问）：

1. 被预设的参数是否稳定到可以只算一次？
2. 最终函数是否有名字（或能被赋给一个命名常量）？
3. 团队里读这行代码的人是否能一眼看出「还缺几个参数才执行」？

三问里有一个答「否」，就用普通函数 + 明确参数。

## 五、常见误区

**1. 把 curry 与 compose / pipeline 混为一谈。**
curry 改变**参数的到达方式**；compose/pipe 改变**函数的串联方向**。判定方法：代码里出现 `f(g(h(x)))` 是组合，出现 `f(a)(b)(c)` 是柯里化。中间件 `compose` 属于后者吗？不属于——它串联的是 `(ctx, next)` 二元函数，没有拆分参数。

**2. 箭头函数版实现丢 `this`。**
下面这个「更简洁」的写法是错的：

```ts
const step = (...received: unknown[]) => {
  if (received.length >= arity) return fn(...received); // 普通调用，this 丢失
  return (...next: unknown[]) => step([...received, ...next]);
};
```

实测用 `curriedThis.call(ctxObj, 'x')('y')` 调用一个依赖 `this.prefix` 的函数，直接抛出：

```text
TypeError: Cannot read properties of undefined (reading 'prefix')
```

原因是箭头函数没有自己的 `this`，`.call(ctx, …)` 传进来的接收者被丢弃。要保住 `this`，必须用函数表达式并显式透传：

```ts
function bind(received: unknown[], thisArg: unknown): unknown {
  return function (this: unknown, ...next: unknown[]): unknown {
    const all = [...received, ...next];
    const self = this === undefined ? thisArg : this;
    if (all.length >= arity) return fn.apply(self, all as unknown as TArgs);
    return bind(all, self);
  };
}
```

实测该版本 `good.call(ctxObj, 'x')('y')` 得到 `[obj]/x/y`。浏览器事件处理器、jQuery 风格插件这类仍依赖 `this` 的 API 会被这个坑命中。

**3. 直接柯里化 `class` 构造函数。**

```ts
const makePoint = curry((x: number, y: number) => new Point(x, y)); // ✅ {"x":1,"y":2}
const curriedCtor = curry(Point); // ❌ 抛错
```

实测后者抛 `TypeError: Class constructor Point cannot be invoked without 'new'`。柯里化后的调用形式是普通函数调用，而 ES class 只允许 `new` 调用。要柯里化构造行为，包一层工厂函数。

**4. 忽略 `fn.length`，把「arity」当作可靠信息。**

```text
['1','2','3'].map(parseInt)                    → [1, NaN, NaN]
['1','2','3'].map((v) => parseInt(v, 10))      → [1, 2, 3]
```

`map` 传的是 `(value, index, array)` 三元参数，`parseInt(string, radix)` 的第二参数被 index 污染。同理，`curry(arr.map)` 这类「arity 大于你意图的函数」必须显式指定 arity。另两个实测值：`curry` 返回的函数 `length === 0`（rest 参数），而原函数 `length === 2`——任何依赖 `length` 的库（compose 工具、测试框架）拿到柯里化结果都会看到 0。

**5. 无限柯里化 + `valueOf`：面试玩具，生产禁用。**

```ts
function addAuto(total: number): AutoAdd {
  const f = ((n: number) => addAuto(total + n)) as AutoAdd;
  f.valueOf = () => total;
  return f;
}
+addAuto(1)(2)(3); // 6
```

实测能跑通（依赖 `+` 触发的隐式 `valueOf`），但它要求调用方记得做类型转换、返回值永远是函数（`if` 判断恒真）、无法被 TS 精确表达。真实需求应当是显式的 `sum()` 终止函数。

**6. 过度柯里化：可读性与调试成本。**
`createUser(validateRole)(parseBody)(persist)` 读起来像咒语。三个具体成本：调用栈深度翻倍（每个中间层都是匿名函数帧）、断点定位从「哪一行」变成「链上的第几层」、TS 错误信息从 `Expected 3 arguments` 变成 `Type 'number' is not assignable to type '(arg: number) => ...'`。**参数语义不同质时才柯里化**（如「配置 / 输入 / 副作用」三层），同质参数（三个坐标）柯里化只有坏处。

**7. 用柯里化实现「默认参数」。**
`curry(f)(a)` 返回一个待执行的函数而不是带默认值的调用结果；把它当默认参数用会导致返回值类型在「结果」与「函数」之间摇摆，调用点必须判断。TypeScript 的可选参数 + 默认值已经解决这个问题，柯里化不是替代品。

## 六、总结

- 柯里化的本质是 `(A×B×C)→R ≅ A→(B→(C→R))` 的形态变换，收益来自**参数到达时间点被拆开**：参数复用、延迟执行、可组合、可特化。
- 实现只有两个关键点：数组累积参数（别用 rest 参数递归）、正确的 arity（`fn.length` 不可靠，必须可覆盖）；保 `this` 需要显式透传接收者。
- TS 侧两种签名各有代价：`Curried<TArgs,R>` 递归条件类型给出精确单元链（`@ts-expect-error` 能挡住 `curry(f)(1,2)`），重载穷举兼容灵活切分但组合数指数增长。
- curry / partial / compose 三者职责不同：拆参数、固定部分参数、串函数。中间件 `compose` 是复合，不是柯里化。
- 与 `memoize` 组合的正确顺序是 `curry(memoize(fn))`；实测两次相同参数只执行一次原函数。
- 判断是否值得柯里化：参数是否稳定、结果是否有名字、读者是否能一眼看出还缺几个参数。三者缺一就退回普通函数。
