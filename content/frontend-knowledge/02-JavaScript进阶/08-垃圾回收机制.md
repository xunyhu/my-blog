# 垃圾回收机制

## 一、是什么

垃圾回收（GC）解决一个问题：**运行时如何判断一块堆内存再也用不到，从而安全复用**。

JS 不提供 `free`，因为「是否还需要」在通用情形下不可判定（停机问题的推论）。于是所有引擎都改用近似：**可达性（reachability）**——从一组已知活跃的根（roots）出发，沿指针能到达的对象必须保留，到不了的对象可以回收。V8 的[官方博客](https://v8.dev/blog/trash-talk)把这件事表述为「用可达性作为存活性的代理（reachability as a proxy for liveness）」。

三个必须先建立的边界认知：

1. **GC 只管 JS 堆。** `ArrayBuffer` 的 backing store、WebAssembly 内存这类外部资源走引擎的 external 记账。实测分配 8MB `Uint8Array` 时 `heapUsed` 纹丝不动，增量全部落在 `external` / `arrayBuffers`（见 3.6）。
2. **DOM 节点由 Blink 的 Oilpan 回收**，不是 V8 的 GC。两个收集器通过 wrapper 互相引用，所以「Detached DOM」泄漏本质是**跨收集器的引用**问题。
3. **回收时机完全由实现决定。** 语言规范只说「可以被回收（may be collected）」，不承诺「何时」。后面所有「弱引用观察规则」都源于这一条。

## 二、为什么

不理解 GC 的前端会写出三类典型问题：

- **长会话内存膨胀**：管理后台、编辑器、地图/大屏类页面运行数小时后卡顿、被系统换页甚至标签页被丢弃。GC 无法回收「你以为释放了但还被引用着」的对象，泄漏唯一的外在表现就是堆增长曲线不回落。
- **卡顿与 INP 变差**：GC 的部分阶段仍需暂停主线程，分配速率越高回收越频繁。理解「短命对象很便宜、长寿对象要复制」才能写出对分代友好的代码。
- **缓存设计错误**：把 `Map` 当无限缓存、或用 `WeakMap` 却期待它有 `size`。前者必然泄漏，后者依赖 GC 时机做业务判断会偶发失败。

反过来说，多数业务代码**不需要**为 GC 做优化。理解它的价值在于：出问题时知道往哪看，写长生命周期对象时知道哪些引用会被意外保留。

## 三、核心原理

### 3.1 V8 堆的分代布局

```text
┌───────────────────────── V8 堆 ─────────────────────────┐
│  新生代 young generation      老生代 old generation       │
│  ┌──────────────┬───────────────┐  ┌───────────────────┐ │
│  │  nursery     │ intermediate  │  │ old space         │ │
│  │ (新分配对象)  │ (活过 1 次 GC) │  │ (活过 2 次即晋升)  │ │
│  ├──────────────┴───────────────┤  ├───────────────────┤ │
│  │ From-Space │ To-Space (空)   │  │ large object space│ │
│  └──────────────────────────────┘  ├───────────────────┤ │
│      Minor GC：Scavenge            │ map space(隐藏类)  │ │
│      （复制式，成本 ∝ 存活对象）      └───────────────────┘ │
│                                     Major GC：Mark-Compact │
└────────────────────────────────────────────────────────────┘

晋升路径：分配到 nursery ──存活 1 次──> intermediate ──再存活──> old generation
```

设计依据是**分代假说（Generational Hypothesis）**：绝大多数对象分配后很快就不可达。复制式回收的代价与**存活对象数量**成正比（而不是与分配数量成正比），把新对象集中在一小块空间里复制，成本自然极低。V8 官方博客的原话是：「每次分配都相当于隐式产生垃圾，我们只为存活的对象付复制成本」。

### 3.2 Minor GC：并行 Scavenge

```text
一次 scavenge（复制存活对象）
From-Space(满)  [A][x][B][y][C]        To-Space(空)  [    ]
      │ 遍历 roots + old-to-new 引用，把活对象复制进 To-Space
      ▼
From-Space(空)  [ ][ ][ ][ ][ ]        To-Space      [A][B][C]
      角色互换：To 成为下次复制的目标；被移动对象留下 forwarding pointer 供指针更新
```

要点（均出自 V8 官方博客）：

- **半空间（semi-space）设计**：始终留一半空间为空以容纳复制结果，最坏情况全部存活即复制一切。
- **二次存活晋升**到老生代，避免半空间被长寿对象占满。
- scavenge 的 roots 除执行栈与全局对象外，还要加上 **old-to-new 引用**（老生代指向新生代的指针）。这些引用**由写屏障维护成一个集合**，因此不必扫描整个老生代——这是写屏障在分代回收里的第一个作用（第二个是并发标记的正确性）。
- 标记、复制、指针更新三步**交错进行**，而非三个独立阶段。
- 现状是**并行 Scavenge**：多线程分配工作，用原子 read/write/CAS 协调「同一个对象被两条路径同时发现」的复制竞争，线程本地分配缓冲（TLAB）避免同步开销。官方给出的收益是新生代 GC 的主线程总时间下降约 **20%–50%**。

### 3.3 Major GC：Mark-Sweep(-Compact)

```text
① Mark    从 roots（执行栈、全局对象）沿指针遍历，标记所有可达对象
② Sweep   把死亡对象留下的空隙按大小归类挂进 free-list，供后续分配复用
③ Compact （选择性）把高碎片页面的存活对象整体搬到别的页面，消除碎片
```

复制（compaction）有代价：大量长寿对象被反复复制会拖慢程序，因此 V8 **只对高碎片页面压缩，其余页面只 sweep**。Major GC 的当前形态是：**并发标记 + 并发清除 + 并行压缩与指针更新**。

### 3.4 三色标记与写屏障：增量/并发为什么可能出错

标记过程可抽象成三色图：

| 颜色  | 含义                          | V8 实现                       |
| ----- | ----------------------------- | ----------------------------- |
| white | 尚未发现；标记结束仍白 → 垃圾 | mark-bit `00`                 |
| grey  | 已发现，但其字段尚未全部扫描  | mark-bit `10`，在 worklist 中 |
| black | 自身与其全部字段都已扫描完成  | mark-bit `11`                 |

```text
初始：全部 white          标记中                 收敛（无 grey）
   ⚪ ⚪ ⚪               ⚫ 🟡 ⚪               ⚫ ⚫ ⚪
    ┆                     ┆   ┆                 ┆  ┆   ┆
   ⚪ ⚪    ← 从 roots     ⚪  ⚪     →    剩下的 white 即为可回收对象
   出发，把 grey 出队染黑，其白依赖染灰入队
```

**标记完成的条件是没有 grey 对象**（V8 用每对象 2 bit 编码这三色 + 一个 marking worklist）。

如果允许应用在标记期间运行，它就可能骗过收集器。经典坏情形是「黑直接指向白、灰路径消失」：

```text
黑 A ──> 白 C            强三色不变式：黑不得直接指向白
   │
   └─(断开) 灰 B ──> 白 C  →  若 B 再无入边，C 会被误判为垃圾
```

V8 在[并发标记博客](https://v8.dev/blog/concurrent-marking)里给出的手段是 **Dijkstra 风格写屏障**，在每次 `object.field = value` 之后插入：

```cpp
// Called after `object.field = value`.
write_barrier(object, field_offset, value) {
  if (color(object) == black && color(value) == white) {
    set_color(value, grey);
    marking_worklist.push(value);
  }
}
```

即「黑对象新指向的白对象立刻染灰重新入队」，从而维持**强三色不变式**。并发标记阶段为了省掉一次内存栅栏（`memory_fence`），把它改成更保守的形式——去掉源对象颜色判断、原子地完成 white→grey 转换：

```cpp
// 并发阶段：atomic_relaxed_write(&object.field, value) 之后
write_barrier(object, field_offset, value) {
  if (color(value) == white && atomic_color_transition(value, white, grey)) {
    marking_worklist.push(value);
  }
}
```

少一个判断意味着**更保守**：可能把实际不可达的对象暂时判为存活（浮动垃圾），换取正确性与吞吐。

### 3.5 Stop-The-World、增量、并发：三种隐藏暂停的方式

```text
STW（早期）   main ──JS──│██████ 一次性标记：大堆可达数百毫秒 ██████│──JS──
增量          main ──JS─│小│─JS─│小│─JS──│小│─JS─│小│──JS──  切成小块插在任务之间
并行          main ──────│████│──  仍是 STW，但 helper 一起干，暂停 ÷ 线程数
并发          main ──JS───JS──JS───JS──  helper 在后台扫描（靠写屏障保证正确）
```

- **增量标记**：V8 于 **2011 年**从 STW 标记切换为增量标记，每块工作量按**应用分配速率**动态选择。在内存压力大、分配飞快的大堆上仍可能出现长暂停——收集器在追赶分配速度。
- **并行**：仍暂停 JS，但主线程与 helper 一起做同样的工作。
- **并发**：主线程继续跑 JS，helper 在后台标记。并发标记于 **Chrome 64 / Node.js v10** 默认启用，官方实测把主线程标记时间降低 **60%–70%**（移动端约 65%、桌面端约 70%）。
- **并非零暂停**：Worker 线程遇到需要独占访问的对象（代码补丁、隐藏类、弱集合）会 **bail out** 到 bailout worklist，这些对象只能在主线程的暂停阶段处理；标记收尾与并行压缩、指针更新同样在暂停中完成。所以「并发 GC」= 把大部分工作挪出主线程 + 保留很短的暂停。
- **空闲期 GC（idle-time GC）**：JS 代码无法触发 GC，但 V8 可以向嵌入方（Chrome）投递「Idle Tasks」，浏览器在一帧提前渲染完的空档执行。官方收益数据：Gmail 空闲时 JS 堆内存下降 **45%**。Node.js 从未实现这种空闲调度，这也是并发标记对 Node 意义尤其大的原因。

一句话记住边界：**增量把暂停切碎，并行把切碎的时间分摊，并发把工作挪出主线程，写屏障是后两者能正确的代价。**

### 3.6 实测：堆里到底放了什么

Node 22.14 下用 `--expose-gc` 跑出的真实数据（`process.memoryUsage()`，单位 MB）：

```text
B0 分配前               heapUsed=7.4  rss=75.1  external=6.8   arrayBuffers=0.0
B1 new Uint8Array(8MB)  heapUsed=7.4  rss=75.1  external=14.8  arrayBuffers=8.0
B2 强制 gc（仍被引用）    heapUsed=7.4  rss=75.1  external=14.8  arrayBuffers=8.0
B3 置 null + gc 后       heapUsed=7.4  rss=75.1  external=6.8   arrayBuffers=0.0
```

结论：`TypedArray` 的缓冲区**不进 `heapUsed`**。只盯 JS 堆会漏掉最大的一块内存——这也是 `performance.memory` 失真的具体来源之一。

同一批实验里，20 万个对象把 `heapUsed` 从 7.4MB 基线推到 **22.6–23.3MB**，闭包释放并强制 GC 后回落到 **7.4MB**（详见 4.1③）。

## 四、工程实践：内存泄漏模式与弱引用工具

### 4.1 六类高频泄漏模式与修法

**① 事件监听 / Observer 未解绑**

```ts
class Panel {
  private readonly ro: ResizeObserver;
  constructor(private el: HTMLElement) {
    this.ro = new ResizeObserver(() => this.relayout()); // 闭包捕获 this
    this.ro.observe(el);
    window.addEventListener('resize', this.onResize);
  }
  dispose(): void {
    this.ro.disconnect();
    window.removeEventListener('resize', this.onResize);
  }
}
```

现代写法用一个 `AbortController` 统一注销，避免漏掉某个 `remove`：

```ts
const ctrl = new AbortController();
el.addEventListener('click', onClick, { signal: ctrl.signal });
window.addEventListener('keydown', onKey, { signal: ctrl.signal });
// 组件卸载 / effect cleanup：ctrl.abort() → 上面所有监听一次性移除
```

**② 定时器 / `rAF` 循环持有大对象**

`setInterval` 的回调永远被定时器持有，它捕获的整条作用域链都不能回收，直到 `clearInterval`。若确实需要「目标消失就自动停」，`WeakRef` 是正解（结构源自 MDN 官方示例）：

```ts
let timer = 0;
let count = 0;
const el = document.getElementById('counter');
const ref = new WeakRef(el!);

const tick = (): void => {
  const node = ref.deref();
  if (node) {
    node.textContent = String(++count);
  } else {
    clearInterval(timer); // 目标已回收 → 自动停止
    console.log('target gone');
  }
};
timer = setInterval(tick, 1000);
```

实测（Node 22.14，目标换成普通对象、配合 `--expose-gc`）：目标被释放后，定时器在下一轮检测到 `deref() === undefined` 并自行 `clearInterval`，输出 `tick 1 -> node-1 | tick 2 -> node-1 | 目标已被回收，自动 stop`。

**③ 闭包过度保留（最隐蔽，也最容易量化）**

```ts
// ❌ 返回的闭包引用了整个 rows，20 万条随闭包常驻
function leaky(): () => number {
  const rows: Array<{ id: number; name: string }> = Array.from(
    { length: 200_000 },
    (_, i) => ({ id: i, name: `row-${i}` }),
  );
  return () => rows.length;
}
// ✅ 只保留需要的摘要值，rows 在函数返回后即可回收
function fixed(): () => number {
  const rows: Array<{ id: number; name: string }> = Array.from(
    { length: 200_000 },
    (_, i) => ({ id: i, name: `row-${i}` }),
  );
  const count = rows.length;
  return () => count;
}
```

实测数据（每步都 `gc()` 并让出一个宏任务后读 `heapUsed`）：

```text
Y0 基线              heap = 7.4 MB
Y1 leaky() 闭包存活   heap = 22.6 MB   ← 20 万条被闭包保留
Y2 leaker = null 后   heap = 7.4 MB    ← 确实可回收，不是"GC 偷懒"
Y3 fixed() 闭包存活   heap = 7.4 MB    ← 只保留 count，rows 已回收
```

同一段数据、同一句 `rows.length`，唯一区别是**闭包捕获的是变量还是值**。这说明「引擎会不会只保留用到的变量」不能靠直觉——上例里 `leaky` 的闭包实实在在保住了整个数组。

**④ 无上限的模块级缓存**

```ts
const cache = new Map<string, Result>(); // 只增不减 → 稳定泄漏
```

三选一：LRU（限条数或字节数）、TTL（`setTimeout` + 删除）、或改用 `WeakMap` 让键决定生命周期。

**⑤ Detached DOM**

节点已从文档移除，但 JS 侧仍持有引用（数组、闭包、`WeakMap` 的**值**、或 Oilpan wrapper）。DOM 由 Blink 回收，「JS 引用 + 原生 wrapper」的链条任一环没断开就会保住整棵子树。排查靠 heap snapshot 里过滤 `Detached` 前缀，或在 **Retainers** 面板看是谁把它拽住。

**⑥ 第三方实例与外部资源**

图表/编辑器实例、WebGL 上下文、Web Worker、`MessageChannel`、`IntersectionObserver`、`MediaQueryList.addListener`——多数都有显式 `dispose/destroy/close/disconnect`。JS 堆监控看不到 GPU 与原生内存，只能用 `measureUserAgentSpecificMemory()` 或浏览器任务管理器观察。

### 4.2 WeakMap：唯一「按键回收」的结构

```ts
const weakListeners = new WeakMap<object, () => void>();
let live: { id: string } | null = { id: 'weak-node' };
weakListeners.set(live, () => {});
const probe = new WeakRef(live);
live = null;
// 让出一个宏任务 + gc() 后
probe.deref() === undefined; // ✅ 实测 true：键被回收，值随之不再驻留
```

适用场景非常明确：**以对象为键的附加数据**——组件实例的内部状态、DOM 节点元信息、私有字段的替代方案。三个限制要知道：键必须是对象（原始值不行）、**没有 `size`、不可遍历**、不能用来「统计还剩几个活对象」（实测另一份强引用 `Map` 存 1000 条时 `size` 恒为 1000，无从判断可回收性）。

### 4.3 WeakRef 与 FinalizationRegistry：观察规则比 API 更重要

`WeakRef.deref()` 返回目标或 `undefined`；`FinalizationRegistry` 在目标回收后回调一个 held value。[MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakRef) 与提案作者反复强调的三条**规范级保证**（而非经验）：

1. **同一 JS job 内看不到回收。**「刚创建 WeakRef、或刚 `deref()` 拿到目标，那么在本 job 结束前目标不会被回收」——只能在**事件循环的另一轮**观察到 `undefined`。
2. **不保证及时，甚至不保证发生。** 分代回收、增量/并发切分、运行时启发式、引擎内部引用（闭包、内联缓存）都会让对象长期存活；「一个 WeakRef 可能永远不返回 `undefined`」。
3. **回调永不同步执行。** 对象可以同步被回收，但清理回调总在当前 job 结束后才可能触发；注册表自身不可达、页面关闭时不会执行。

实测印证（同一环境、三份脚本）：

```text
[实验一] 轮询 deref 观察
A2 最终 deref = [object Object]           ← 反复 tick+gc 也没观察到回收

[实验二] 交给 FinalizationRegistry + 跨轮 settle
X1 回调已触发 = ["c","a","b"] | 三个 deref = undefined,undefined,undefined
X2 丢弃 WeakRef 句柄本身后，回调 = ["c","a","b"]

[实验三] 单轮与及时性
G5 同一 job 内 deref 仍可见 = { name: 'ephemeral' }
G6 同步 gc() 后 deref 仍可见（同 job 不观察回收）
G7 让出事件循环 + gc() 后 deref 仍可见
G11 weakCache 中仍可 deref = 50（弱引用不保证及时性）
G12 registry 可达时的回调次数 = 1
```

同样的代码，一个实验「一个都没观察到」、另一个「三个全观察到」，差别只在**是否让出事件循环、以及是否在轮询中反复 `deref`**——正是第 1 条规则的具象表现，也是「GC 行为不可依赖」的最好证据。

由此得出使用准则：

- ✅ 可以：`WeakRef` 做**尽力而为的缓存**（命中省算力、miss 重算）；`WeakMap` 存对象附加数据；`FinalizationRegistry` 做**可选的**原生资源释放提醒。
- ❌ 不可：把终结回调当**唯一**的资源清理路径（必须有显式 `dispose()`）；用 `deref() === undefined` 推断「对象销毁了所以槽位可复用」这类业务逻辑；写依赖 GC 时序的测试。

### 4.4 测量：四件工具与它们的失真

**① Chrome DevTools Memory 面板**（[官方文档](https://developer.chrome.com/docs/devtools/memory)）

- **Heap snapshot**：某时刻的对象分布与 Retainers 引用链。判泄漏用「三次快照法」：基线 → 重复操作 N 次并回到初始状态 → 强制 GC → 快照 A → 再操作一轮 → 回到初始状态 → 快照 B。**比较 A 与 B**，仍单调增长的对象类型基本就是泄漏点。
- **Allocation instrumentation on timeline**：按时间轴记录分配、被 GC 回收的部分显示为浅色，适合定位「点击后涨了不回落」，能给出分配调用栈。
- **Allocation sampling**：开销低，适合回答「谁分配得最多」，但不反映回收结果。
- 配合 `Detached` 过滤找脱离 DOM、用 Comparison 视图看 delta、用 Retainers 找引用者。

**② `performance.measureUserAgentSpecificMemory()`** —— 线上 RUM 的正解，但门槛明确：

```js
if (crossOriginIsolated) {
  const { bytes, breakdown } =
    await performance.measureUserAgentSpecificMemory();
  report({ bytes, page: location.pathname });
}

// 推荐做法：随机化间隔的周期采样，而不是单次调用
function runMemoryMeasurements() {
  const interval = -Math.log(Math.random()) * 5 * 60 * 1000; // 指数分布，均值 5 分钟
  setTimeout(measureMemory, interval);
}
async function measureMemory() {
  report(await performance.measureUserAgentSpecificMemory());
  runMemoryMeasurements();
}
```

必须知道的限制（MDN + web.dev）：需要**安全上下文 + cross-origin isolation**（COOP/COEP），否则抛 `SecurityError`；**仅 Chromium 系实现（自 Chrome 89 起）**，Safari / Firefox 未支持，MDN 标注为实验性且**非 Baseline**；返回字节数**跨浏览器、甚至同浏览器不同版本都不可比**，`breakdown` 的 `types` / `attribution` 由实现自定义；它能覆盖 iframe 与 worker，这正是相对 `performance.memory` 的优势。

**③ `performance.memory`** —— 已弃用、非标准、**仅 Chromium**，且只反映 JS 堆。MDN 明确说明：共享同一堆的页面会**高估**、使用 worker / 跨站 iframe 的页面会**低估**，并直接建议改用 `measureUserAgentSpecificMemory()`。拿它当线上内存指标属于历史包袱，新代码不应再引入。

**④ Node / 边缘运行时**

```text
process.memoryUsage()  → rss, heapTotal, heapUsed, external, arrayBuffers
v8.getHeapStatistics() → used_heap_size, heap_size_limit, total_physical_size,
                         total_available_size, external_memory, malloced_memory,
                         number_of_native_contexts, number_of_detached_contexts
实测本机最小进程：used_heap_size ≈ 3.7MB，heap_size_limit ≈ 4144MB（默认老生代上限）
实测 Node 中 performance.memory 与 measureUserAgentSpecificMemory 均为 undefined
```

`--expose-gc` 提供 `globalThis.gc()`（仅调试，会显著扭曲性能）；`--max-old-space-size` 决定老生代上限，超限即 OOM 崩溃。`number_of_detached_contexts` 在 Node 侧是「上下文泄漏」的粗粒度信号。

**排查决策树：**

```text
内存相关问题
├─ 只在本机复现？ → Memory 面板：三次快照 → Retainers 找引用者
├─ 线上才有？     → 满足 crossOriginIsolated 后周期采样 measureUserAgentSpecificMemory，
│                   按路由 / 会话时长分桶看 P95 曲线（只比趋势，不比绝对值）
├─ 涨但不卡？     → 先分清"分配器保留"（正常锯齿）与"引用残留"（三次快照比对）
└─ 卡顿为主？     → Performance 面板看 GC 事件密度与 Major GC 时长，
                    再回到"降低分配速率"而不是"帮 GC 回收"上想办法
```

### 4.5 对 GC 友好的写法

V8 官方的建议值得原样吸收：**短命对象很便宜**，因为只为存活对象付复制成本。工程含义：

- 不要在渲染循环里维护「长期存活的大数组 + 频繁整体替换」；大数据放 `TypedArray` / 缓冲池，并注意 `external` / `arrayBuffers` 的记账。
- 保持对象**形状（hidden class）稳定**：构造函数里一次声明所有字段、避免运行时随机附加属性，让内联缓存与 GC 的字段扫描都更可预测。
- 分块处理大数据（`setTimeout` / 微任务切片）不仅降 INP，也让 GC 工作分散到多个周期。
- 缓存必须显式选择失效策略（LRU / TTL / WeakMap），别指望 GC 替你淘汰——GC 只回收**不可达**的对象，被 `Map` 引用的对象永远可达。

## 五、常见误区

**1. 「引用计数已淘汰，所以循环引用不再是问题」——一半对。**
现代引擎按可达性回收，`a.ref = b; b.ref = a` 在两者都不可达时能被正确回收。但跨收集器边界（JS 对象 ↔ DOM wrapper ↔ Oilpan）的老式案例、以及「循环 + 一个外部锚点」仍表现为泄漏。说「JS 里循环引用绝对安全」是过度简化。

**2. 「内存增长 = 泄漏」。**
free-list 保留、半空间交换、并发阶段产生的浮动垃圾都会让堆曲线呈锯齿。判定要看**回到同一业务状态并强制 GC 后是否回落**（本文 Y2 回落到 7.4MB 是健康的；不回落才是泄漏）。

**3. 期待 `gc()` 之后 `deref()` 立刻变 `undefined`。**
实测同一 job 内 `gc()` 后 deref 仍返回对象（G5/G6），让出一个宏任务后也可能仍可见（G7、A2）。规范只承诺「跨 job 才能观察到」，从不承诺及时性。用轮询 `deref` 做检测，结论完全依赖引擎当下的启发式——这正是我在这组实验里同时得到「三个都回收」和「一个都没回收」的原因。

**4. 以为 `WeakMap` 有 `size`、可遍历、可用于统计。**
它没有。想知道「还剩几个活跃对象」只能自己配 `FinalizationRegistry` 计数，而这个计数**天生可能少报或迟到**，不能用于业务正确性判断。

**5. 用 `FinalizationRegistry` 代替显式释放。**
终结回调可能永远不执行（页面关闭、注册表不可达、内存压力不足）。原生资源（句柄、GPU buffer、Worker）必须有 `dispose()` 主路径，终结回调只能作为「漏掉了也不致命」的兜底告警。

**6. 用 `performance.memory` 或单次采样做线上内存指标。**
非标准 + 仅 Chromium + 共享堆失真 + 不含外部内存。要么满足跨域隔离改用 `measureUserAgentSpecificMemory()`，并接受「仅 Chromium、跨浏览器不可比」；要么明确自己只看趋势不看绝对值。

**7. 想「在浏览器里主动触发 GC」。**
没有 `window.gc()`；DevTools 面板的强制回收按钮只影响面板。若某些逻辑必须在回收后才成立，说明设计错了——改成显式清理。

**8. 对 `delete obj.x` / `arr.length = 0` 的行为想当然。**
`arr.length = 0` 确实释放元素引用（实测 5 万个对象从 19.6MB 回落到 7.4MB）；而 `delete obj.x` 只删属性，并可能改变对象形状（隐藏类退化，连带影响内联缓存）。反过来，**数组变量置为 `null` 但闭包仍引用它**时什么也不会释放——「谁还引用着」永远比「我清了哪个变量」重要。

**9. 为了 GC 而过度复用对象。**
对象池在 JS 里收益有限（分代回收对短命对象已经很便宜），却引入状态污染风险。只有在实测 Major GC 时长或分配速率确实是瓶颈时才做。

## 六、总结

- GC 的判定标准是**可达性**，不是「没人用了」；roots 是执行栈 + 全局对象，新生代还额外需要「老生代指向新生代的引用集合」（由写屏障维护）。
- V8 采用**分代 + mostly concurrent & parallel（Orinoco）**：Minor GC = 并行 Scavenge（半空间、二次存活晋升、只为存活对象付复制成本）；Major GC = 并发标记 + 并发清除 + 并行压缩。
- 三色标记（white/grey/black，2 bit 编码 + worklist）在允许 mutator 运行时必须靠**写屏障**维持强三色不变式；增量把暂停切碎（2011 年起），并行分摊时间，并发把工作挪出主线程（Chrome 64 / Node 10，主线程标记时间 -60%~70%），但 bailout 与压缩阶段仍有短暂停。
- 弱引用三件套的定位：`WeakMap` 做按键回收的附加数据、`WeakRef` 做尽力而为的缓存与「目标没了就自停」的循环、`FinalizationRegistry` 做可选清理提醒；三者都受「跨 job 才可观察、不保证及时、可能永不发生」的约束。
- 泄漏六大类：监听器/Observer、定时器闭包、闭包保留大对象、无上限缓存、Detached DOM、第三方实例。测量按场景选：三次 heap snapshot（本地）、`measureUserAgentSpecificMemory`（线上，需跨域隔离、仅 Chromium）、`process.memoryUsage` / `v8.getHeapStatistics`（Node，注意 `external` / `arrayBuffers` 不在 `heapUsed` 里）。
