# 防抖与节流

## 一、是什么

两者都是**用「丢弃或延后执行」换取主线程与后端压力下降**的频率控制手段，区别只在**什么时候允许执行**。

```text
事件序列（每个 ▲ 是一次事件，频率远高于处理能力）
t =    0    50   100   150   200   250   300   350   400   450   500 (ms)
       ▲    ▲    ▲           ▲     ▲     ▲                   ▲
       │    │    │           │     │     │                   │

debounce(wait=200, trailing)   └──┘  └──┘  └─────┘  静默期不足 → 定时器一直重置
                              ● 只在"停止 200ms"后执行 1 次，且用最后一次参数

throttle(wait=200, leading+trailing)
       ●            ●             ●          每 200ms 最多 1 次，
                                             窗口内保留最新参数

rAF 节流
       ●                ●    ●               窗口 = 一帧（≈16.7ms），
                                             由浏览器刷新节奏驱动
```

三个必须一起理解的维度，缺任何一个都会写出「平时能跑、边界条件下出错」的实现：

| 选项       | 含义                                     | 典型用途                     |
| ---------- | ---------------------------------------- | ---------------------------- |
| `leading`  | 静默期**开始时**立即执行一次             | 按钮防连点、提交             |
| `trailing` | 静默期**结束时**用最后参数执行           | 搜索输入、resize 后重排      |
| `maxWait`  | 无论是否仍在触发，最多累积这么久强制输出 | 滚动埋点、连续输入的自动保存 |

lodash 语义下 `debounce` 默认 `leading: false, trailing: true`；`throttle` 等价于 `debounce(fn, wait, { maxWait: wait })` 的便捷封装。这个等价关系是理解二者最好的切入点：**throttle 就是加了上限的 debounce**。

## 二、为什么

问题的根源是**事件频率与处理成本不匹配**：

- `input` 在快速输入时可达 10–30 次/秒，而一次搜索请求的成本是网络往返 + 后端查询。
- `scroll` / `wheel` / `touchmove` 在高刷屏上可达 120 次/秒；回调里若有 `getBoundingClientRect()` 或样式写入，会与样式、布局阶段串成强制同步布局。
- `resize` 在拖拽窗口时连续触发，而重排一个复杂表格是 10ms 级别。
- 埋点、自动保存、WebSocket 心跳这类「状态变更后要同步出去」的逻辑，逐次触发会把后端 QPS 放大一个数量级。

代价体现在三层：主线程占用（掉帧、INP 变差）、网络与后端放大（重复请求、竞态、幂等压力）、以及**用户可感知的反馈错误**（滚动位置计算丢失、保存的不是最终版本）。

反过来也必须清楚：**防抖节流不降低单次处理的成本，只减少处理次数**。一次处理本身要 300ms，限频之后应用照样卡。

## 三、核心原理

### 3.1 触发时机差在哪

```text
                 wait = 100ms，事件在 0 / 30 / 60ms 连续到来

debounce         每次事件都把定时器重新排到 t+100
  0──30──60────────────────160
  ▲   ▲   ▲                  ●   ← 执行 1 次，参数取 60ms 那次

debounce + leading
  ●                          ●   ← 0ms 立即一次，静默结束后再一次
  ▲   ▲   ▲

debounce + maxWait = 200（事件每 25ms 一直来，静默期永不成立）
  0    25   50 ... 200 ... 400 ... 600
  ▲    ▲    ▲      ●       ●       ●   ← 靠 maxWait 强制输出

throttle（窗口对齐）
  0    25   50   75   100  125 ...
  ●              ▲    ▲    ▲          ← 0ms leading 立即，
                                         窗口末尾用最新参数补一次
```

关键差别一句话：**debounce 的时钟被每次事件重置（关心「何时停止」），throttle 的时钟独立推进（关心「多久一次」）**。

### 3.2 可运行的 debounce

支持 `leading` / `trailing` / `maxWait` 与 `cancel` / `flush` / `pending`。以下代码在 Node 22.14 下用 11 组时间线场景验证过（实测数据见 3.5）：

```ts
export interface DebounceOptions {
  leading?: boolean;
  trailing?: boolean;
  maxWait?: number;
}

export type Procedure<TArgs extends unknown[]> = (
  this: unknown,
  ...args: TArgs
) => unknown;

export interface RateLimited<TArgs extends unknown[]> {
  (this: unknown, ...args: TArgs): void;
  cancel(): void;
  flush(): void;
  pending(): boolean;
}

type Timer = ReturnType<typeof setTimeout> | null;

export function debounce<TArgs extends unknown[]>(
  fn: Procedure<TArgs>,
  wait: number,
  options: DebounceOptions = {},
): RateLimited<TArgs> {
  const { leading = false, trailing = true, maxWait } = options;
  const maxing = maxWait !== undefined;

  let timer: Timer = null;
  let lastArgs: TArgs | null = null;
  let lastThis: unknown = null;
  let lastCallTime = 0;
  let lastInvokeTime = 0; // 0 表示从未执行过

  function invoke(time: number): void {
    lastInvokeTime = time;
    const args = lastArgs;
    const thisArg = lastThis;
    lastArgs = null;
    lastThis = null;
    if (args) fn.call(thisArg, ...args); // 注意是 .call：保住调用方的 this
  }

  // sinceCall < 0 兼容系统休眠 / 时钟回拨：时间倒退时应当立即执行而不是永不执行
  function shouldInvoke(time: number): boolean {
    const sinceCall = time - lastCallTime;
    const sinceInvoke = time - lastInvokeTime;
    return (
      sinceCall >= wait || sinceCall < 0 || (maxing && sinceInvoke >= maxWait!)
    );
  }

  function remainingWait(time: number): number {
    const waiting = wait - (time - lastCallTime);
    return maxing
      ? Math.min(waiting, maxWait! - (time - lastInvokeTime))
      : waiting;
  }

  function timerExpired(): void {
    const time = Date.now();
    if (shouldInvoke(time)) {
      timer = null;
      if (trailing && lastArgs) invoke(time);
      else {
        lastArgs = null;
        lastThis = null;
      }
      return;
    }
    timer = setTimeout(timerExpired, Math.max(0, remainingWait(time)));
  }

  const debounced = function (this: unknown, ...args: TArgs): void {
    const time = Date.now();
    lastArgs = args;
    lastThis = this;
    lastCallTime = time;

    if (timer === null) {
      if (maxing && lastInvokeTime === 0) lastInvokeTime = time;
      if (leading) invoke(time);
      timer = setTimeout(timerExpired, wait);
      return;
    }
    // 已有定时器在跑：maxWait 是否到期交给 shouldInvoke 判定，避免在调用点重复执行
  } as RateLimited<TArgs>;

  debounced.cancel = (): void => {
    if (timer) clearTimeout(timer);
    timer = null;
    lastArgs = null;
    lastThis = null;
  };
  debounced.flush = (): void => {
    if (timer) {
      clearTimeout(timer);
      timer = null;
      if (lastArgs) invoke(Date.now());
    }
  };
  debounced.pending = (): boolean => timer !== null;
  return debounced;
}
```

四个容易写错的点：

1. **必须保存 `lastArgs`，而不是靠每次调用各自的闭包。** 网上常见的 `timer = setTimeout(() => fn(...args), wait)` 写法虽然「也能跑」，但它无法实现 `leading`、`flush`，也无法在 `trailing: false` 时正确丢弃待执行参数——因为参数已经被每个闭包分别持有了。
2. **`lastThis` 与 `lastArgs` 同生命周期**，`invoke` 后立刻清空，否则 `this` 会泄漏到上一个调用者对象。
3. **`maxWait` 的等待时间取 `min(wait剩余, maxWait剩余)`**（`remainingWait`），而不是再起一个独立的 `setTimeout(maxWait)`。两套独立定时器会互相抢着执行，出现同一批事件输出两次。
4. **`timerExpired` 里要二次判断 `shouldInvoke`**：定时器的到期时刻不等于「静默期真的结束」（可能有休眠、时钟误差、`maxWait` 先到期），不满足时按 `remainingWait` 重新排。

### 3.3 可运行的 throttle（窗口对齐版）

不要写「`Date.now() - last > wait` 就执行」的无尾调用版本（会丢最后一次事件，见第五节第 2 条）。定时器版：

```ts
export function throttle<TArgs extends unknown[]>(
  fn: Procedure<TArgs>,
  wait: number,
  options: { leading?: boolean; trailing?: boolean } = {},
): RateLimited<TArgs> {
  const { leading = true, trailing = true } = options;

  let timer: Timer = null;
  let lastArgs: TArgs | null = null;
  let lastThis: unknown = null;
  let lastInvokeTime = 0;

  function invoke(time: number): void {
    lastInvokeTime = time;
    const args = lastArgs;
    const thisArg = lastThis;
    lastArgs = null;
    lastThis = null;
    if (args) fn.call(thisArg, ...args);
  }

  const throttled = function (this: unknown, ...args: TArgs): void {
    const time = Date.now();
    lastArgs = args;
    lastThis = this;

    if (timer !== null) return; // 本窗口已排队
    const firstWindow = lastInvokeTime === 0;
    if (firstWindow && leading) {
      invoke(time);
      return;
    }
    const remaining = firstWindow ? wait : wait - (time - lastInvokeTime);
    if (remaining <= 0) {
      invoke(time); // 距上次执行已超过 wait，直接放行
      return;
    }
    if (trailing) {
      timer = setTimeout(() => {
        timer = null;
        if (lastArgs) invoke(Date.now());
      }, remaining);
    }
  } as RateLimited<TArgs>;

  throttled.cancel = (): void => {
    if (timer) clearTimeout(timer);
    timer = null;
    lastArgs = null;
    lastThis = null;
  };
  throttled.flush = (): void => {
    if (timer) {
      clearTimeout(timer);
      timer = null;
      if (lastArgs) invoke(Date.now());
    }
  };
  throttled.pending = (): boolean => timer !== null;
  return throttled;
}
```

尾调用的延迟用 `remaining`（窗口剩余时间）而不是固定 `wait`，输出才对齐「距上次执行满 wait」的语义；否则会每轮再往后偏一个完整 wait。

### 3.4 为什么必须提供 cancel / flush / pending

限频函数把状态藏进了闭包（定时器 + 待执行参数 + 时间戳），外部无法安全获取：

- `cancel()`：组件卸载、用户放弃输入、路由离开时丢弃未执行的调用。
- `flush()`：页面隐藏 / 提交前，把攒着的那一次立刻输出。
- `pending()`：判断是否还有排队，用于「有未保存内容」提示与 unload 守卫。

没有这三个方法的 debounce，在 SPA 里一定会泄漏定时器或丢最后一次请求。

### 3.5 实测时间线（Node 22.14，`wait=100`，事件间隔 25–30ms）

| 场景                      | 事件时刻                                         | 实测执行时刻（相对起点）             |
| ------------------------- | ------------------------------------------------ | ------------------------------------ |
| debounce 默认             | 0                                                | `+100ms`                             |
| debounce 默认，连续三次   | 0, 30, 60                                        | `+164ms`（仅一次，参数取第 3 次）    |
| `leading: true`           | 0；静默后再来 200                                | `+0ms`、`+202ms`                     |
| `leading + trailing`      | 0, 30, 60                                        | `+0ms`、`+163ms`                     |
| `leading, trailing:false` | 0, 30                                            | `+0ms`（只有一次）                   |
| `maxWait: 200`            | 每 25ms 连续 24 次                               | `+202ms`、`+403ms`、`+605ms`         |
| cancel / flush / pending  | 调用后 `true`，cancel 后 `false`，flush 立即输出 | `+205ms`                             |
| throttle 默认             | 每 25ms 连续 12 次                               | `+0ms`、`+100ms`、`+200ms`、`+302ms` |
| throttle `leading:false`  | 每 25ms                                          | `+101ms`、`+202ms`、`+303ms`         |
| throttle `trailing:false` | 每 25ms                                          | `+0ms`、`+104ms`、`+208ms`           |
| throttle 稀疏调用         | 0, 300                                           | `+0ms`、`+301ms`（各一次 leading）   |

同一批测试还验证了 `this` 与参数保真：用 `debounced.call(box, 'hurui.dev', 2)` 触发，回调里 `this.name` 与两个参数原样到达（`invoke this.name=search-box, args=hurui.dev,2`）。换成 `fn(...args)` 时 `this` 变成 `undefined`，且因为执行被推迟，堆栈已经和触发点对不上。

> 表中毫秒含 Node 定时器粒度误差（通常 +2~5ms），用于验证**相对时序**，不是绝对精度。

## 四、工程实践

### 4.1 React 中的正确写法：实例必须跨渲染存活

最常见的 bug 是让限频函数每次渲染都新建——每个实例有自己的定时器与闭包状态，**等于完全没防抖**。

```tsx
'use client';

import { useEffect, useMemo, useRef } from 'react';

export function useDebouncedCallback<A extends unknown[]>(
  fn: (...args: A) => void,
  wait: number,
) {
  // 用 ref 持有"最新的 fn"：debounce 实例只创建一次，回调又不会读到旧闭包
  const fnRef = useRef(fn);
  fnRef.current = fn;

  const debounced = useMemo(
    () =>
      debounce((...args: A) => {
        fnRef.current(...args);
      }, wait),
    [wait],
  );

  // 搜索类场景：卸载时丢弃未执行的调用（保存/埋点类场景应改成 flush，见 4.6）
  useEffect(() => () => debounced.cancel(), [debounced]);

  return debounced;
}
```

两个反例及各自暴露的问题：

```tsx
// ❌ 每次渲染都新建实例：定时器互不知情，10 次渲染 = 10 个待执行定时器
const onInput = debounce((v) => setQuery(v), 300);

// ❌ 闭包 stale：实例创建时的 query 被冻结，回调读到的是旧值
const onSearch = useMemo(() => debounce(() => api.search(query), 300), []);
```

第二条是典型的 stale closure：限频函数天然把执行推迟到未来，而它捕获的是**过去某次渲染**的作用域。解法两类——把变化的值列进依赖数组（但会导致实例重建，需配合 `pending()` 决定是否先 flush），或者用 `useRef` / 函数式更新读当前值。上面代码选后者。

### 4.2 与 `useDeferredValue` / `startTransition` 的边界

React 官方文档专门对比过三者（[useDeferredValue — 与 debounce/throttle 的区别](https://react.dev/reference/react/useDeferredValue)），结论值得原样吸收：

| 维度         | debounce / throttle            | `useDeferredValue`                       |
| ------------ | ------------------------------ | ---------------------------------------- |
| 延迟由谁决定 | 你写死的毫秒数                 | 设备与渲染耗时：快设备几乎立刻更新       |
| 是否可中断   | 否，回调一旦执行就阻塞到底     | 是，React 可放弃进行中的渲染去响应新按键 |
| 优化对象     | **副作用 / 网络请求**的次数    | **渲染本身**的开销（降级为后台渲染）     |
| 对输入的阻塞 | 仍阻塞（只是推迟了阻塞的时刻） | 不阻塞                                   |

判据：**昂贵的事情发生在渲染阶段就用并发特性；昂贵的事情是请求、DOM 读写、计算副作用就用限频**。两者可叠加：输入用 `debounce(300, { maxWait: 1000 })` 发请求，返回的长列表用 `useDeferredValue` 渲染。

### 4.3 `resize` 交给 ResizeObserver

`window` 的 `resize` 只知道视口变了，不知道**哪个元素**变了尺寸；侧边栏折叠、字体加载、容器查询都会改变元素尺寸却不触发 `resize`。[ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver) 是 Baseline 广泛可用特性（主流浏览器自 2020 年 7 月起支持），应当作为默认选择：

```ts
const ro = new ResizeObserver((entries) => {
  // 回调在"绘制之前"执行；若回调里再次修改被观察元素的尺寸会形成循环，
  // 浏览器会把未送达的通知推迟到下一帧并抛 "ResizeObserver loop completed with undelivered notifications."
  requestAnimationFrame(() => {
    for (const entry of entries) {
      const width =
        entry.contentBoxSize?.[0]?.inlineSize ?? entry.contentRect.width;
      layout(width); // 需要限频的重排逻辑放这里
    }
  });
});
ro.observe(el);
// 卸载：ro.disconnect()，或只针对单个元素 ro.unobserve(el)
```

两个实践细节：用 `requestAnimationFrame` 包裹回调是官方文档给出的打断循环手段；如果只想在尺寸**稳定后**重排，就在回调内部再套一层 debounce（`ResizeObserver` 负责「看到变化」，debounce 负责「等变化停下」），而不是继续用 `window.addEventListener('resize', debounce(...))`。

### 4.4 `requestIdleCallback`：可用，但必须特性检测

低优先级工作（预取、序列化缓存、非关键埋点落盘）适合放空闲期。但它**不是 Baseline 特性**：Chrome 47+ / Edge 79+ / Firefox 55+ 支持，而 Safari 从 13.1 到 27.x 稳定版一直是「默认关闭」（仅 Technology Preview 可用）。所以必须写降级：

```ts
export function scheduleLowPriority(work: () => void): () => void {
  const w = typeof window === 'undefined' ? null : window;

  if (w && typeof w.requestIdleCallback === 'function') {
    const id = w.requestIdleCallback(
      (deadline) => {
        if (deadline.timeRemaining() > 8 || deadline.didTimeout) work();
        else w.requestIdleCallback(() => work(), { timeout: 500 }); // 本帧剩余不足，顺延
      },
      { timeout: 1000 }, // 必须给 timeout：否则可能几秒都不执行
    );
    return () => w.cancelIdleCallback(id);
  }

  // Safari 稳定版路径：退让到下一个宏任务，不假装自己"空闲"
  const id = setTimeout(work, 1);
  return () => clearTimeout(id);
}
```

MDN 明确提示 `timeout` 对「必须完成的工作」是强烈建议项，否则回调可能延后数秒才执行。它与 debounce 不是替代关系：debounce 控制「做几次」，idle 控制「在主线程的哪个位置做」。

### 4.5 搜索请求：debounce + 取消 + 竞态防护

限频只解决「请求太多」，不解决「回来的顺序不对」。三段都要写：

```ts
const inflight = useRef<AbortController | null>(null);
const seq = useRef(0);

const runSearch = useMemo(
  () =>
    debounce(
      async (q: string) => {
        inflight.current?.abort(); // 取消上一次仍在飞的请求
        const ctrl = new AbortController();
        inflight.current = ctrl;
        const myId = ++seq.current;

        const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
          signal: ctrl.signal,
        });
        const data = (await res.json()) as { items: string[] };
        if (myId !== seq.current) return; // 序号落后 → 迟到的响应直接丢弃
        setItems(data.items);
      },
      300,
      { maxWait: 1000 },
    ),
  [],
);
```

`maxWait` 在这里的意义：用户连续输入 3 秒时，仍保证每秒有一次结果更新，而不是「停手才出结果」。

### 4.6 埋点与自动保存：靠 `maxWait` + 页面隐藏 flush

```ts
const track = debounce(send, 2000, { maxWait: 10000 });

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') track.flush();
});
// pagehide 里配合 navigator.sendBeacon，避免请求被页面销毁中断
window.addEventListener('pagehide', () => track.flush());
```

`flush()` 是限频函数必须暴露它的最强理由：页面生命周期结束的时刻，是「攒着的那一次」唯一确定的出口。也正因如此，4.1 里的卸载清理要按语义选：搜索框 `cancel`（用户已放弃，旧查询发出去反而污染结果），自动保存/埋点 `flush`（最后状态必须落地）。

### 4.7 滚动 / 触摸：`passive` + `rAF` 节流

```ts
let ticking = false;

const onScroll = (): void => {
  if (ticking) return; // 本帧已经排过一次，直接丢弃后续事件
  ticking = true;
  requestAnimationFrame(() => {
    ticking = false;
    updateIndicator(window.scrollY); // 用"最后一帧时最新的位置"计算
  });
};
window.addEventListener('scroll', onScroll, { passive: true });
```

`passive: true` 告诉浏览器不会调用 `preventDefault()`，滚动合成不必等待回调；`ticking` 标志把频率钉在刷新率上。对**必须看到最终位置**的逻辑（例如「滚动停了再加载」），在 `rAF` 之外再叠一层 debounce 收尾——这是 throttle 与 debounce 协作而非二选一的地方。

## 五、常见误区

**1. 每次渲染 / 每次绑定都新建限频函数。**
`element.addEventListener('scroll', throttle(fn, 100))` 写在组件函数体里，等于每次渲染都注册一个新监听、每个 throttle 各自计数，表现为「防抖完全无效」。修法：实例化一次（`useMemo` 或模块作用域），卸载时 `removeEventListener` + `cancel()`。

**2. 只有 `trailing` 意识的实现被当成 throttle。**
「时间差够了就执行，否则什么都不做」的写法在事件停止时不再补一次——最后一次输入的值永远丢。这不是节流，是**采样且丢尾**。判定方法：连续高频事件停止后，是否还有一次以最新参数执行的调用（实测 T1 在 `+302ms` 补了尾调用）。

**3. 把 debounce 当性能优化的全部。**
`scroll` 回调里做 DOM 读写，debounce 100ms 之后仍然读写一次，只是从「每帧」变成「每 100ms」。真正解决问题的是降低单次成本（`IntersectionObserver` 替代手动计算、CSS `position: sticky` 替代 JS 定位）。限频降低**频率**，不降低**单价**。

**4. 用 debounce 处理需要即时反馈的交互。**
按钮提交应当 `leading: true`（首次立即执行、后续静默）；配成默认 trailing 会让用户等 300ms 才看到响应——这不是优化，是引入延迟。拖动进度条、画板笔迹这类「过程即结果」的交互不能 debounce，只能 throttle 或 `rAF`。

**5. 误把 `leading: true, trailing: false` 当「双保险」。**
实测该组合在连续事件下**只执行一次**（`+0ms`），静默结束不补。若业务需要「必须拿到最终值」，它会静默丢结果。反之 `leading: false, trailing: false` 等于什么都不做。所有配置组合都该像本文那样跑一遍时间线。

**6. 不给 `maxWait`，让 debounce 变成无限等待。**
用户持续输入 10 秒，纯 trailing 的 debounce 一次都不执行，自动保存形同虚设。凡是「持续触发 + 需要中途输出」的场景都要 `maxWait`（实测每约 200ms 强制输出一轮）。

**7. 卸载清理一律写 `cancel()`（或一律写 `flush()`）。**
两种语义对应两类需求，见 4.6。写死一种，另一类需求就会丢数据或发多余请求。

**8. 忽略定时器泄漏与 `this` 丢失。**
没有 `cancel` 的 debounce 在路由切换后仍会触发回调，访问已卸载组件的 state；`fn(...args)` 而非 `fn.call(thisArg, ...args)` 会让依赖 `this` 的类方法/DOM handler 崩在延迟执行的时刻——而且堆栈已与触发点对不上，排查成本极高。

**9. 以为限频能省后端算力。**
客户端 debounce 只挡住自己这一路；多标签页、多设备、脚本直连照样会放大。服务端侧的合并、去重、幂等与背压是另一层，不能因为前端做了 debounce 就省掉。

## 六、总结

- 本质区别一句话：debounce 的时钟随事件重置（关心「什么时候停下来」），throttle 的时钟独立推进（关心「多久输出一次」）；`throttle(fn, w)` ≡ `debounce(fn, w, { maxWait: w })`。
- 完整实现必须覆盖 `leading` / `trailing` / `maxWait` 与 `cancel` / `flush` / `pending`，显式透传 `this` 与最新参数，并保留 `sinceCall < 0` 这类时钟回拨分支。
- 在 React 里，限频函数是**跨渲染的有状态对象**：`useMemo` 保证实例唯一，`useRef` 打破 stale closure，`useEffect` 清理按语义决定 cancel 还是 flush。
- 渲染开销交给 `useDeferredValue` / `startTransition`（自适应设备、可中断）；副作用与请求交给限频；`ResizeObserver` 负责观察尺寸；`requestIdleCallback` 负责安排低优先级时机（Safari 稳定版不可用，必须降级）。
- 用时间线方法验收：连续高频 → 输出次数是否 ≈ 事件数 / wait；事件停止 → 是否补最后一次；持续 10 倍 `wait` → `maxWait` 是否兜住；卸载 → 定时器是否清零。
