# 代码分割

## 一、是什么

代码分割把应用划分为多个可加载单元，让用户先获取当前任务需要的部分，再加载其他功能。
它通常降低首屏 JavaScript 成本，但不自动减少整站代码总量。

要区分三个动作：

- **分包**：构建器把模块放进不同 chunk。
- **加载**：浏览器获取 chunk，可能由导航、预取或交互触发。
- **执行**：模块求值和组件渲染，下载结束不代表交互已经完成。

`import()` 提供异步模块加载语义，bundler 再将可分析的导入映射为相应资源。
浏览器原生 ESM 也支持 `import()`，并非只有 Webpack 才能使用。

## 二、为什么

一个只有少数人打开的图表、编辑器或导出工具，不应默认占据所有用户的首屏关键路径。
但把每个按钮拆成一个 chunk，又会增加请求、调度与依赖瀑布。

合适的边界通常符合“功能大、初始不需要、有清晰交互入口”。
首屏主内容、关键导航、LCP 图片相关逻辑则不宜为了分包而延后。

```text
未分割
HTML -> app + editor + chart -> 解析执行 -> 首屏可交互

按功能分割
HTML -> app -> 首屏可交互
           |
           +-> 点击图表 -> chart -> 渲染图表
           |
           +-> 点击编辑 -> editor -> 渲染编辑器
```

这只是依赖关系图，不是耗时承诺。
必须比较首屏传输量、解析时间、打开功能的等待时间与失败率，才能判断是否值得。

## 三、核心原理

### import 的异步语义

`import()` 返回 Promise，成功值是模块命名空间对象。
顶层求值会在模块加载时发生，同一模块通常被运行时缓存。
重复调用不代表重新下载或重新执行初始化。

构建器需要知道可能导入什么：

```js
const loaders = {
  chart: () => import('@/app/components/demo/Report'),
  editor: () => import('@/app/components/demo/Editor'),
};

export async function loadFeature(name) {
  const load = Object.hasOwn(loaders, name) ? loaders[name] : undefined;
  if (!load) throw new Error('Unknown feature');
  return load();
}
```

这里假定教学应用已实现两个组件，展示的是静态导入映射，不是本站现有模块。
不要把用户输入直接拼进模块路径；静态映射既限制加载范围，也让构建器发现边界。
部分工具支持有限的变量导入，但可能建立很大的上下文依赖集合。

### React 的加载与错误边界

`React.lazy(load)` 延后加载组件，要求 Promise 最终得到含 `default` 组件的对象。
应在模块顶层声明 lazy 组件，而不是在 render 内反复创建新组件类型。

```text
首次尝试渲染 lazy 组件
          |
          v
       load()
       /    \
 pending   rejected -> Error Boundary -> 降级界面
   |
   v
Suspense fallback
   |
 fulfilled
   |
   v
default 组件渲染
```

Suspense 处理“还在等待”，Error Boundary 处理“加载或渲染失败”。
React 会缓存 lazy 的 Promise 和结果；仅重置一个错误边界，不保证重新发起失败的加载。
事件处理函数里自行调用的 Promise 也不由 Error Boundary 自动捕获，应显式 `try/catch`。

### Next.js App Router 的边界

本站锁定 Next.js 16.1.7，使用 App Router；以下依据官方 lazy loading 文档核对。
服务端组件默认按路由等边界组织，流式渲染还可以逐步返回 UI。
服务端模块通常不进入客户端 JS；真正影响客户端包的是客户端边界及其传递依赖。

`'use client'` 声明客户端模块边界，不等于“永远不在服务器预渲染”。
`next/dynamic` 组合了 React lazy 与 Suspense 相关能力，客户端组件默认仍可以预渲染。
`ssr: false` 只应放在客户端组件内，用于确实依赖浏览器环境的组件。

官方目前明确说明：从 Server Component 动态导入 Client Component，不能据此保证自动客户端代码分割。
要延迟大型客户端功能，通常在小型 Client Component 包装层中声明 dynamic，再由交互决定是否渲染。
不要给整个页面加 `'use client'`，把本可留在服务端的 Markdown 读取逻辑带入客户端。

路由预取可能提前下载资源，因此“第一次点击没有新请求”并不证明分包失败。
`loading.tsx` 是路由加载体验边界，也不等于把所有依赖都推迟到点击之后。

## 四、实践

### 无文件实验验证导入缓存与失败

以下完整示例使用 Node 22，运行方式为 `node --input-type=module`，从标准输入粘贴执行。
它验证模块语义，不模拟真实浏览器的 chunk 下载。

```js
import assert from 'node:assert/strict';

const source = `
  globalThis.__splitRuns = (globalThis.__splitRuns ?? 0) + 1;
  export default (a, b) => a + b;
`;
const url = `data:text/javascript,${encodeURIComponent(source)}`;
const first = await import(url);
const second = await import(url);
assert.equal(first, second);
assert.equal(first.default(2, 3), 5);
assert.equal(globalThis.__splitRuns, 1);

const broken = 'data:text/javascript,throw%20new%20Error(%22demo-failure%22)';
await assert.rejects(import(broken), /demo-failure/);
delete globalThis.__splitRuns;
console.log('dynamic import assertions passed');
```

模块顶层的业务异常也会让 import Promise 拒绝。
所以看到“动态导入失败”时，不能直接判定为断网或 CDN 404。

### React lazy 的完整交互样例

以下两个文件用于已有 React 19、支持 JSX 与 `@/` 别名的教学应用。
在 Next 教学应用中，也可以直接把外层组件引入页面；不要覆盖本站现有组件。

被加载组件的位置为 `app/components/demo/Report.jsx`：

```jsx
'use client';

export default function Report() {
  return (
    <section aria-label="年度报表">
      <h2>年度报表</h2>
      <p>销售额：120 万元</p>
    </section>
  );
}
```

外层组件的位置为 `app/components/demo/LazyPanel.jsx`：

```jsx
'use client';

import { Component, Suspense, lazy, useState } from 'react';

const Report = lazy(() => import('@/app/components/demo/Report'));

class FeatureBoundary extends Component {
  state = { failed: false };

  static getDerivedStateFromError() {
    return { failed: true };
  }

  componentDidCatch(error) {
    // 教学环境输出；生产应走统一监控并去重、脱敏。
    console.error('report unavailable', error);
  }

  render() {
    if (this.state.failed) {
      return (
        <div role="alert">
          <p>报表暂时不可用，请先保存其他工作。</p>
          <button onClick={() => window.location.reload()}>
            确认已保存并刷新
          </button>
        </div>
      );
    }
    return this.props.children;
  }
}

export default function LazyPanel() {
  const [open, setOpen] = useState(false);
  return (
    <section>
      <button onClick={() => setOpen(true)} disabled={open}>
        打开报表
      </button>
      {open && (
        <FeatureBoundary>
          <Suspense fallback={<p role="status">正在加载报表…</p>}>
            <Report />
          </Suspense>
        </FeatureBoundary>
      )}
    </section>
  );
}
```

例子选择“用户确认后刷新”，不是自动无限重试，也不假装清空边界状态能清空模块缓存。
对编辑器类功能，应先保存草稿或提供下载入口，再让用户刷新。

### Next dynamic 的替代写法

在 Next.js 教学应用中，可用下面组件替代上面的 LazyPanel；复用同一个 Report 文件。
这里为了展示浏览器专用功能的边界，显式关闭 SSR；普通报表若不访问浏览器 API，应优先保留默认 SSR。

```jsx
'use client';

import dynamic from 'next/dynamic';
import { useState } from 'react';

const Report = dynamic(() => import('@/app/components/demo/Report'), {
  ssr: false,
  loading: () => <p role="status">正在加载报表…</p>,
});

export default function DynamicPanel() {
  const [open, setOpen] = useState(false);
  return (
    <section>
      <button onClick={() => setOpen(true)}>打开报表</button>
      {open && <Report />}
    </section>
  );
}
```

实际接入时仍应在功能外层添加前例那样的 Error Boundary，或者使用适当的路由错误边界。
`loading` 回调是等待态，不是错误恢复策略。
若模块只有命名导出，可用 `.then((module) => module.Report)` 提供组件；不要误取整个模块对象。

### 工程实践与 chunk 失败治理

常见失败链路如下：

```text
用户保留版本 A 的页面
          |
发布版本 B，并删除 A 的旧资源
          |
旧页面点击尚未加载的功能
          |
请求 A-hash.js -> 404 -> import 拒绝 -> 功能不可用
```

需要区分版本错配、离线、CSP 拦截、CDN 返回 HTML、MIME 类型错误与模块求值异常。
记录脱敏后的资源路径、发布版本、浏览器和失败阶段；错误名称可能是 `ChunkLoadError`，也可能只是 `TypeError`。
不能只匹配一个错误字符串，就认定所有浏览器和 bundler 的加载失败都被覆盖。

发布端应先上传带内容哈希的资源，再切换 HTML 或路由版本，并保留旧资源一段合理时间。
Next 多实例部署还需要一致的构建产物、发布标识及缓存策略；平台的版本错配保护不能只靠客户端重试代替。
具体保留周期取决于页面会话长度、CDN 缓存与回滚窗口。

暂时断网可以提供有限重试提示，但已删除的 chunk 不会因立即重试而复活。
不要给构建器管理的 chunk 随意追加随机 query，试图绕过其 manifest 和运行时缓存。
避免应用启动、错误边界和全局监听同时刷新，形成刷新风暴。

验收应在生产构建上进行：

1. 禁用缓存查看首屏请求，再允许缓存检查二次打开。
2. 延迟大资源，观察 fallback 是否稳定、有可读状态且不导致布局跳动。
3. 阻断一个异步资源，验证错误界面可用且主页面仍能操作。
4. 保留旧标签页并发布新版，验证旧资源窗口和恢复入口。
5. 比较首屏收益与打开功能的等待成本，而非只看 chunk 数量。

## 五、误区

- **拆得越细越快。** 小 chunk 的请求和解析调度也有成本，依赖链可能变得更深。
- **lazy 自动捕获失败。** 它把拒绝交给错误边界；Suspense 只解决等待。
- **use client 就是关闭 SSR。** 客户端边界与预渲染开关是不同概念。
- **dynamic 声明后必然等点击才下载。** 立即渲染、路由预取和框架预加载都可能提前获取。
- **刷新能修复所有 chunk 错误。** CSP、部署路径和持续故障不会因刷新自然消失。

## 六、总结

代码分割的目标是优化用户任务的关键路径，而不是追求更多文件。
可靠方案需要同时设计模块边界、等待态、错误态与发布兼容窗口。
