# 前端监控

## 一、是什么

前端监控是持续收集运行信号、定位用户受损原因并验证修复效果的工程系统。
它不等于在每个 catch 中调用一次上报，也不等于把用户所有行为都记录下来。

基本信号可以分为：

| 信号          | 解决的问题         | 典型内容                   |
| ------------- | ------------------ | -------------------------- |
| 错误事件      | 哪个功能失败了     | 异常类型、堆栈、发布版本   |
| 性能指标      | 用户体验是否退化   | LCP、INP、CLS、路由耗时    |
| Trace 与 span | 时间花在何处       | 页面导航、请求、关键计算   |
| 行为上下文    | 错误发生前做了什么 | 经审核的低基数操作名       |
| 会话回放      | 如何复现交互过程   | 单独授权、遮蔽后的页面变化 |

本文核对日期为 2026-10-02，SDK 示例明确固定为 `@sentry/nextjs@10.57.0`。
它使用现代函数式 API 和该版本支持的 `dataCollection`，不使用旧 `new BrowserTracing()`。
本站 `package.json` 与锁文件没有安装 Sentry；下文是独立接入方案，不是已经上线的本站功能。

## 二、为什么

用户不会总能提供复现步骤，浏览器控制台也不会自动把生产错误交给维护者。
如果只有错误数量，无法区分“请求量增长”和“故障率增长”。
如果只有平均耗时，又容易掩盖低端设备或长尾用户受到的影响。

一个有效闭环至少需要：

1. 使用发布版本、环境、低基数路由标签关联同一问题。
2. 用 source map 将压缩堆栈还原为可定位的源码位置。
3. 按受影响会话、失败率和持续时间制定告警。
4. 验证新版本是否改善，而不是收到事件后直接忽略。
5. 在采集前限制数据范围、成本和访问权限。

## 三、核心原理

### 从异常到修复

```text
Browser / React / Next server / Edge
                  |
          各运行时的 SDK 初始化
                  |
        捕获 -> 补充发布信息 -> 脱敏
                  |
       错误采样 / Trace 采样 / 回放采样
                  |
           transport -> Sentry
                  |
        事件分组 + source map 还原
                  |
           告警 -> 修复 -> 验证
```

采样与脱敏的具体执行顺序由 SDK 管线决定；不能把某个 hook 当作所有数据产品的统一出口。
例如 `beforeSend` 面向错误事件，不会自动清理所有 Trace、日志和 Replay 数据。

### SDK 不能混用

| 应用形态         | SDK 与入口                                   | 不该做的事                          |
| ---------------- | -------------------------------------------- | ----------------------------------- |
| 无框架浏览器应用 | `@sentry/browser`，启动入口初始化            | 期待自动理解 React 错误边界         |
| 自管 React SPA   | `@sentry/react`，根入口与 React 错误处理集成 | 在 Next 内自行创建第二个 React root |
| Next App Router  | `@sentry/nextjs`，客户端及服务端分别初始化   | 只初始化浏览器就宣称能捕获 RSC 错误 |
| Node 服务        | 对应 Node SDK 或框架 SDK                     | 在 Edge 包中引入 Node 专用模块      |

普通 React SPA 可使用 `browserTracingIntegration()`；Next SDK 应按其框架指南配置导航与服务端插桩。
不要把 SPA 的路由集成、Next 的 instrumentation 和旧版教程混合复制。
同时装多个 SDK 并重复 init，容易产生重复事件、重复监听和不同的上下文。

### 性能与采样的不同口径

Core Web Vitals 包含 LCP、INP、CLS，关注加载、交互和布局稳定性。
应按真实用户数据、设备分组和第 75 百分位观察，而非用某一次本机 Lighthouse 成绩代替线上结论。

`PerformanceObserver` 可以观察 navigation、resource、longtask 等受浏览器支持的 entry。
但把最大一条 event duration 直接命名为 INP 不正确：指标还有交互聚合、页面生命周期等规则。
需要完整 CWV 时优先使用经过维护的指标实现，详见[前端性能优化](/knowledge/03-浏览器与网络/10-前端性能优化)。

采样必须分别规划：

- `sampleRate`：错误事件的采样率，不是 Trace 采样率。
- `tracesSampleRate`：性能 Trace 的基线采样率。
- `tracesSampler`：按上下文决策；配置后优先于固定 Trace 采样率。
- Replay 的 session 与 on-error 采样：决定回放录制，不由错误采样率替代。

采样率 0.1 不代表每 10 个用户恰好取 1 个，也不能让原始事件数直接等于总体故障数。
需要结合请求量、会话量、丢弃事件统计和采样偏差看趋势。

## 四、实践

### 接入前提与版本边界

下列文件是**独立 Next.js 16.1.7 App Router 接入示例**，不是要求修改本站。
在测试项目安装 `npm install --save-exact @sentry/nextjs@10.57.0`，提交该项目锁文件后再接入。
Node 可使用本站的 22.14.0；不要安装不受运行时支持的新 SDK 主版本后继续照抄旧配置。

这个版本从 `@sentry/nextjs` 导出 `withSentryConfig`。
最新文档可能展示 `@sentry/nextjs/config`，但 10.57.0 的包导出表没有该子路径，因此这里使用已核对的根导出。
`dataCollection` 从 10.57.0 提供；该版本将 `sendDefaultPii` 标为弃用，不能只照搬旧版隐私默认值。

必要环境变量如下：

| 变量                                      | 用途                       | 暴露范围                             |
| ----------------------------------------- | -------------------------- | ------------------------------------ |
| `NEXT_PUBLIC_SENTRY_DSN`                  | 浏览器事件接收地址         | 可公开，但应配置接收侧限额与允许来源 |
| `SENTRY_DSN`                              | 服务端事件接收地址         | 服务端环境                           |
| `NEXT_PUBLIC_APP_RELEASE` / `APP_RELEASE` | 同一个发布标识，如 Git SHA | 两端一致；浏览器值在构建时固化       |
| `NEXT_PUBLIC_APP_ENV` / `APP_ENV`         | preview、production 等     | 构建端与运行端明确设置               |
| `SENTRY_ORG` / `SENTRY_PROJECT`           | source map 上传目标        | 构建环境                             |
| `SENTRY_AUTH_TOKEN`                       | source map 上传凭据        | 仅可信 CI secret，绝不能加公开前缀   |

DSN 不是上传管理令牌；把 DSN 隐藏起来也不能代替服务端配额控制。

### 共享的最小采集策略

测试项目 `lib/monitoring-options.ts`，三种运行时共同引用：

```ts
import * as Sentry from '@sentry/nextjs';

export const monitoringOptions = {
  sampleRate: 1,
  tracesSampleRate: 0.05,
  enableLogs: false,
  maxBreadcrumbs: 20,
  dataCollection: {
    userInfo: false,
    cookies: false,
    httpHeaders: false,
    httpBodies: [],
    urlQueryParams: false,
    graphQL: { document: false, variables: false },
    genAI: { inputs: false, outputs: false },
    databaseQueryData: false,
    queues: false,
    stackFrameVariables: false,
    frameContextLines: 0,
  },
  beforeBreadcrumb() {
    // 初次上线不采集自动行为面包屑，审核后再按类别放行。
    return null;
  },
  beforeSend(event) {
    delete event.user;
    delete event.extra;
    delete event.request;
    delete event.message;
    for (const exception of event.exception?.values ?? []) {
      // 防止 Error.message 混入表单内容；保留异常类型与堆栈。
      exception.value = 'Application error';
    }
    return event;
  },
  beforeSendTransaction(event) {
    delete event.user;
    delete event.extra;
    delete event.request;
    // 这里不擅自改写框架的 span 结构；上线前审核名称与属性。
    return event;
  },
} satisfies Parameters<typeof Sentry.init>[0];
```

5% 只是起始预算，不是适合所有业务的推荐常数。
这份策略有意牺牲一部分诊断上下文以降低首次接入风险。
它也不是“绝对不会泄露”的保证：自定义 tags、contexts、span 名称、路径片段仍可能含个人信息。
所有人工设置字段都应使用允许清单，避免写入邮箱、订单正文、查询词和鉴权头。

### 客户端与服务端初始化

测试项目根目录 `instrumentation-client.ts`：

```ts
import * as Sentry from '@sentry/nextjs';
import { monitoringOptions } from '@/lib/monitoring-options';

Sentry.init({
  ...monitoringOptions,
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment: process.env.NEXT_PUBLIC_APP_ENV ?? 'development',
  release: process.env.NEXT_PUBLIC_APP_RELEASE,
  // 首轮接入不安装 Replay integration。
  replaysSessionSampleRate: 0,
  replaysOnErrorSampleRate: 0,
});

export const onRouterTransitionStart = Sentry.captureRouterTransitionStart;
```

`instrumentation-client.ts` 在客户端启动时初始化，不能移到普通组件 render 内重复执行。
框架级错误遥测也要遵循业务适用的告知、同意和数据处理政策；需要事先同意的场景应延后初始化。

测试项目 `sentry.server.config.ts`：

```ts
import * as Sentry from '@sentry/nextjs';
import { monitoringOptions } from '@/lib/monitoring-options';

Sentry.init({
  ...monitoringOptions,
  dsn: process.env.SENTRY_DSN,
  environment: process.env.APP_ENV ?? 'development',
  release: process.env.APP_RELEASE,
});
```

测试项目 `sentry.edge.config.ts` 使用同一段初始化代码，作为独立文件由 Edge 路径加载。
不要在该共享配置中引入 `node:fs`、数据库连接或 Node 专用日志库。

测试项目根目录 `instrumentation.ts`：

```ts
import * as Sentry from '@sentry/nextjs';

export async function register() {
  if (process.env.NEXT_RUNTIME === 'nodejs') {
    await import('@/sentry.server.config');
  }
  if (process.env.NEXT_RUNTIME === 'edge') {
    await import('@/sentry.edge.config');
  }
}

export const onRequestError = Sentry.captureRequestError;
```

这样浏览器、Node 和 Edge 各自得到正确的 SDK 初始化。
`onRequestError` 捕获服务端请求路径上的错误，不是业务失败返回值的自动告警器。

### 渲染错误与手动错误

测试项目 `app/global-error.tsx`：

```tsx
'use client';

import * as Sentry from '@sentry/nextjs';
import { useEffect } from 'react';

export default function GlobalError({ error }: { error: Error }) {
  useEffect(() => {
    Sentry.captureException(error);
  }, [error]);

  return (
    <html lang="zh">
      <body>
        <h1>页面暂时不可用</h1>
        <p>请稍后重试，未提交的数据请先保留。</p>
      </body>
    </html>
  );
}
```

全局错误页会替换根布局，所以必须提供自己的 html 和 body。
模块级 `error.tsx` 可提供更小范围的恢复；业务 catch 后不再抛出的异常需要显式捕获。
不要同时在 catch、全局监听与错误边界重复上报同一次失败。

下面的函数可放入已初始化 SDK 的客户端模块，并从测试按钮调用：

```ts
import * as Sentry from '@sentry/nextjs';

export async function verifyMonitoring() {
  return Sentry.startSpan(
    { name: 'monitoring.verify', op: 'ui.action' },
    async () => {
      try {
        throw new Error('Controlled monitoring verification');
      } catch (error) {
        const eventId = Sentry.captureException(error, {
          tags: { feature: 'monitoring-demo' },
        });
        return { eventId };
      }
    },
  );
}
```

这是确定性的测试异常，不会调用业务接口或写入用户数据。
非生产验证环境可临时将 Trace 采样设为 1，确认 span 出现后再恢复预算。
拿到 eventId 不代表服务端一定收到了事件，必须在 Network 和 Sentry 项目中确认。

### source map 与工程实践

测试项目 `next.config.ts`，实际项目应合并原配置而非丢弃已有设置：

```ts
import type { NextConfig } from 'next';
import { withSentryConfig } from '@sentry/nextjs';

const nextConfig: NextConfig = {};

export default withSentryConfig(nextConfig, {
  org: process.env.SENTRY_ORG,
  project: process.env.SENTRY_PROJECT,
  authToken: process.env.SENTRY_AUTH_TOKEN,
  silent: !process.env.CI,
});
```

该 SDK 版本与 Next 16.1.7 满足官方 Turbopack source map 上传的版本前提。
只有生产构建才验证上传路径；开发堆栈可读不代表生产压缩堆栈能还原。
必须把上传的 map 与实际部署的 JS 来自**同一次构建**，避免重建后映射错位。

发布验收要触发一个受控错误，确认原始文件、行号、release 和环境均正确。
检查公开资源端点是否暴露不需要公开的 map；不能把“上传成功”等同于“公网一定不可访问”。
构建端令牌应最小授权，不向 fork PR 提供，也不打印在日志或客户端 bundle。

错误事件通常先保留较高采样，以免低流量的新错误被漏掉；高频已知噪声按明确规则过滤。
过滤 AbortError 等取消操作前，先确认它确实来自用户主动取消，不要按名字一刀切掩盖超时。
Trace 可按关键路径提高采样，跨服务还应协调上游决策，避免整条链路只剩零散片段。

Replay 如确需启用，应单独评审同意机制、保留周期、访问权限和配额。
使用 `replayIntegration({ maskAllText: true, maskAllInputs: true, blockAllMedia: true })` 是起点，不应随意解除遮蔽。
其隐私选项不受 `dataCollection` 统一控制，错误发生时的回放采样也可能显著增加成本。

### 无 SDK 的本地性能与脱敏实验

下面代码可在支持 Performance API 的浏览器控制台运行，也可在 Node 22 执行其中的路径断言。
不发送任何网络请求，不依赖本站安装 Sentry。

```js
function routeLabel(input) {
  try {
    const url = new URL(input, 'https://example.invalid');
    if (url.pathname.startsWith('/knowledge/')) return '/knowledge/[...slug]';
    if (url.pathname.startsWith('/ai-engineer/'))
      return '/ai-engineer/[...slug]';
    return '/other';
  } catch {
    return '/invalid';
  }
}

if (routeLabel('/knowledge/private?token=secret') !== '/knowledge/[...slug]') {
  throw new Error('Route label leaked details');
}
if (routeLabel('/users/alice@example.invalid') !== '/other') {
  throw new Error('Unexpected route label');
}
console.log('privacy assertions passed');

if (typeof PerformanceObserver !== 'undefined') {
  const supported = PerformanceObserver.supportedEntryTypes;
  if (supported.includes('navigation')) {
    const observer = new PerformanceObserver((list) => {
      for (const entry of list.getEntries()) {
        console.log({
          route: routeLabel(entry.name),
          duration: entry.duration,
        });
      }
      observer.disconnect();
    });
    observer.observe({ type: 'navigation', buffered: true });
  }
}
```

这是导航耗时观察，不是 INP 计算，也不能仅凭 observer 回调推出整个页面体验。
实际应用应在卸载或监控停止时清理观察器；上报失败不应再触发同一个上报器递归报错。

## 五、误区

- **初始化浏览器 SDK 就覆盖全栈。** RSC、Route Handler 与 Edge 有不同运行时入口。
- **关闭默认个人信息即可完全合规。** 自定义消息、URL、span 属性和回放仍需逐项审核。
- **beforeSend 控制一切。** Trace、日志、Replay 有不同的数据管线与采样配置。
- **每个异常都应唤醒值班者。** 应综合失败率、影响会话和关键路径，而非只按原始次数告警。
- **装了 SDK 就算完成。** 还需验证收件、去重、source map、配额、隐私和修复后的效果。

## 六、总结

可靠监控需要正确的运行时接入、可还原的堆栈、可解释的采样和明确的数据边界。
先完成受控错误到平台定位的闭环，再逐步增加性能维度与经过审核的上下文。
