# 性能优化

## 一、是什么

**React 性能优化的本质，是减少「不必要的重新渲染（re-render）」与「单次渲染的工作量」。** 它不是零散的技巧堆砌，而是围绕「React 如何决定渲染什么、渲染多少」这条主线展开的系统工程。

需要先厘清一个前提：**「re-render」不等于「操作 DOM」。** React 组件函数被重新调用（re-render）后，会经过 diff 才决定是否真正改 DOM。很多「卡顿」发生在 re-render 与 diff 阶段，而非 DOM 阶段。

## 二、为什么

一次更新涉及 React 协调、提交和浏览器渲染；Effect 是提交后的同步工作，不能把浏览器 layout/paint 算作 React commit 的步骤：

```text
① Render（渲染/协调阶段，可中断）
   调用组件函数 → 生成新的虚拟 DOM → 与旧树 diff（reconciliation）
   切入点：减少被调用的组件数（memo）、减少 diff 规模（拆分/虚拟化）
        │
② Commit（提交阶段，不可中断）
   把 diff 结果应用到真实 DOM → 处理 ref / useLayoutEffect
   切入点：减少 DOM 变更量、避免强制同步布局（读写分离）
        │
③ 浏览器按需执行样式计算 / layout / paint / 合成；useEffect 在提交后运行，不保证总在 paint 后
   切入点：正确依赖、及时清理、避免 Effect 里做重活
```

组件树越大、状态越靠近根部，一次 setState 波及的 re-render 范围就越广——这是绝大多数性能问题的根源。

## 三、核心原理

### 1. 什么会触发 re-render

一个组件重新渲染，通常由以下之一引起：

- 自身 `state` 变化；
- 父组件 re-render（**默认行为：父渲染则子渲染，无论 props 是否变化**）；
- 订阅的 Context value 变化；
- 强制更新（`forceUpdate` / 根节点重渲染）。

> 关键认知：**「父组件渲染 → 所有子组件默认跟着渲染」** 是 React 的默认策略。优化的核心，就是在合适的位置「切断」这条无差别的渲染传播。

### 2. 引用相等性是记忆的命门

`memo`/`useMemo`/`useCallback` 都依赖「浅比较 props / 依赖」。而**每次渲染都会新建的对象、数组、函数字面量，引用都不同**，会让记忆化失效：

```jsx
// ❌ 每次渲染 style 和 onClick 都是「新引用」，Child 的 memo 白做
<Child style={{ color: 'red' }} onClick={() => doSomething(id)} />;

// ✅ 用 useMemo/useCallback 稳定引用，memo 才生效
const style = useMemo(() => ({ color: 'red' }), []);
const onClick = useCallback(() => doSomething(id), [id]);
<Child style={style} onClick={onClick} />;
```

## 四、优化手段

### 1. 记忆化三件套

| API           | 记忆的东西     | 典型用途                         |
| ------------- | -------------- | -------------------------------- |
| `React.memo`  | 组件的渲染结果 | props 未变时跳过子组件 re-render |
| `useMemo`     | 计算值         | 缓存昂贵计算、稳定对象/数组引用  |
| `useCallback` | 函数           | 稳定回调引用，配合子组件 memo    |

```jsx
const Row = React.memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});
```

### 2. React Compiler：独立构建工具的自动记忆化

**React Compiler 是独立的构建时工具，不随 React 19 自动启用。** 显式接入后，它可自动记忆化组件与计算，减少手写缓存：

```ts
// Next.js 16：先显式安装开发依赖 babel-plugin-react-compiler，再配置
const nextConfig = { reactCompiler: true };
export default nextConfig;
```

它要求组件遵循 React 规则。Next.js 16 支持稳定配置，但仍需 `npm install -D babel-plugin-react-compiler`。本仓库当前未安装该依赖、未配置开关；这里只介绍接入方式，不修改工程。存量缓存应验证后再移除。

### 3. 状态下沉与内容提升（最有效的结构优化）

比 memo 更根本的，是**让状态待在最靠近使用它的地方**，缩小 re-render 波及范围：

```jsx
// ❌ 状态在顶层，输入时整棵树（含昂贵的 List）都 re-render
function Page() {
  const [text, setText] = useState('');
  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <ExpensiveList />
    </>
  );
}

// ✅ 状态下沉：输入只重渲染它自己所在的子树
function SearchInput() {
  const [text, setText] = useState('');
  return <input value={text} onChange={(e) => setText(e.target.value)} />;
}
function Page() {
  return (
    <>
      <SearchInput />
      <ExpensiveList />
    </>
  ); // List 不受输入影响
}
```

**内容提升（children 模式）**：把不依赖状态的昂贵 JSX 作为 `children` 传入，父组件 state 变化时它不会重建：

```jsx
function Wrapper({ children }) {
  const [open, setOpen] = useState(false);
  return <div onClick={() => setOpen(!open)}>{children}</div>; // children 引用稳定，不重渲染
}
```

### 4. 并发调度：降低更新优先级而非异步执行计算

`startTransition` 的回调立即执行。它降低状态更新的优先级，不能让同步 `search()` 异步执行或被中断；单次 JS 计算仍可能阻塞输入。下例是组件内片段，只更新查询状态：

```jsx
const [isPending, startTransition] = useTransition();
function onChange(e) {
  setInput(e.target.value); // 紧急
  startTransition(() => setQuery(e.target.value)); // 查询状态交给低优先级渲染
}
```

### 5. 代码分割与懒加载

用 `React.lazy` + `Suspense` 按路由/组件拆包，减少首屏 JS：

```jsx
const Chart = React.lazy(() => import('./Chart'));
<Suspense fallback={<Skeleton />}>
  <Chart />
</Suspense>;
```

Server Component 自身实现不发送到客户端，但其引用的 Client Component 仍有客户端 JS，RSC Payload 也有成本。详见 [服务端组件 RSC](/knowledge/04-React体系/09-服务端组件RSC)。

### 6. 长列表虚拟化

上千行的列表**不要全量渲染 DOM**。用虚拟滚动（`react-window`/`@tanstack/react-virtual`）只渲染可视区节点，把 DOM 规模从 O(n) 降到 O(可视数)。

### 7. key 的正确使用

`key` 决定 diff 时节点的复用与身份：

- ✅ 用**稳定且唯一**的业务 id 作 key；
- ❌ 用数组 `index` 作 key（列表会增删/重排时，导致状态错乱与无谓重渲染）。

## 五、工程实践：列表优化与测量

**假设场景**：搜索 2000 条数据时出现卡顿。下面 Before/After 均为方案片段，缺少 `DATA`、导入及 `VirtualList` 实现，不能直接运行；不代表本仓库实测。后文提供无需虚拟列表库的完整 Profiler 实验。

```jsx
// ❌ Before：输入触发整页 re-render，2000 行全部重新 diff
function Search() {
  const [q, setQ] = useState('');
  const list = DATA.filter((d) => d.name.includes(q));
  return (
    <>
      <input value={q} onChange={(e) => setQ(e.target.value)} />
      <ul>
        {list.map((item) => (
          <li key={item.id}>{item.name}</li>
        ))}
      </ul>
    </>
  );
}
```

候选优化组合（应逐项测量，不是一组必然有效的结论）：

```jsx
// ✅ After
const Row = React.memo(({ item }) => <li>{item.name}</li>); // ① 行级 memo
function Search() {
  const [q, setQ] = useState('');
  const deferredQ = useDeferredValue(q); // ② 输入紧急、过滤降级
  const list = useMemo(
    () => DATA.filter((d) => d.name.includes(deferredQ)),
    [deferredQ],
  ); // ③ 缓存过滤
  return (
    <>
      <input value={q} onChange={(e) => setQ(e.target.value)} />
      <VirtualList items={list} component={Row} /> {/* ④ 虚拟化 */}
    </>
  );
}
```

- **① 行 memo**：未变化的行跳过 re-render；
- **② useDeferredValue**：允许列表暂用旧查询值，降低新列表渲染优先级；单次同步 filter 仍不可中断，重计算需考虑 Worker 或分片；
- **③ useMemo**：`deferredQ` 未变且缓存可用时复用过滤结果；
- **④ 虚拟化**：DOM 只保留可视区数十行。

上述方案只是假设，是否改善延迟必须测量。Compiler 可优化部分缓存，不能替代虚拟化，也不会把同步过滤变成后台线程。

### 常见误区

- **误区一：到处加 `useMemo`/`useCallback` 就一定更快。** 记忆化本身有成本（存依赖、做比较）。对廉价计算或稳定不变的子树，加 memo 反而更慢——**先测量，再优化**。
- **误区二：`React.memo` 包了就万事大吉。** 若传入的 props 每次都是新引用（对象/数组/函数字面量），memo 浅比较必然失败，等于没包。
- **误区三：把状态放在最外层方便共享。** 这会让无关子树被卷入 re-render。应「状态下沉」，或用 Context 精细拆分。
- **误区四：用 `index` 当 key。** 列表增删/重排时会引发状态错位与额外渲染。
- **误区五：一上来就虚拟化。** 虚拟列表有滚动/测量成本，几百行内通常不必；先做结构优化（下沉/memo/并发），DOM 规模确实是瓶颈时再虚拟化。
- **误区六：以为开了 Compiler 就可以不讲规则。** Compiler 只对「符合 React 规则的纯组件」生效，副作用与外部可变状态仍会导致 bug 与被跳过编译。

### 优化策略小结

- React 性能优化围绕**减少不必要 re-render + 降低单次渲染工作量**，分别检查协调、提交、Effect 与浏览器渲染。
- 结构层面优先：**状态下沉、内容提升（children）** 比事后 memo 更根本。
- 记忆化三件套（`memo`/`useMemo`/`useCallback`）依赖**引用相等性**；显式启用 **React Compiler** 后可自动化部分缓存。
- 并发调度调整更新优先级，不打断单次同步计算；首屏体积考虑**代码分割 / RSC**，DOM 规模瓶颈考虑**虚拟化**。
- 一切以**测量**为前提：先用 Profiler 定位真正昂贵的组件，再针对性优化。

> 性能优化的最高境界不是「加更多 memo」，而是**让状态和数据待在正确的地方**——渲染范围小了，优化自然就少了。

### Profiler 自包含实验

前面的代码是局部模式说明：需补齐导入及外部组件，状态下沉的两个 `Page` 是互斥版本，不能粘贴在同一模块。
下面才是可直接作为已有 React 项目 `App.jsx` 或 Next.js 客户端页面的完整模块，只依赖 React。
数据、计算函数、组件和统计都在同一代码块内，无 `DATA` / `VirtualList` 等未定义占位。
它比较“无关状态更新时普通子组件与 memo 子组件的渲染”，不声称验证了虚拟化或整个搜索系统。

```jsx
'use client';

import { Profiler, memo, useRef, useState } from 'react';

const items = Array.from({ length: 2000 }, (_, id) => ({
  id,
  name: `item-${id}`,
}));

function calculate(query) {
  const matches = items.filter((item) => item.name.includes(query));
  let checksum = 0;
  for (const item of matches) {
    for (let i = 0; i < 500; i++) {
      checksum = (checksum + item.id * i) % 1000003;
    }
  }
  return { matches, checksum };
}

function SlowList({ query }) {
  'use no memo'; // 避免已接入 Compiler 的实验环境自动优化此对照
  const { matches, checksum } = calculate(query);
  return (
    <div>
      <p>
        匹配 {matches.length} 条，校验值 {checksum}
      </p>
      <ul>
        {matches.slice(0, 20).map((item) => (
          <li key={item.id}>{item.name}</li>
        ))}
      </ul>
    </div>
  );
}

const MemoList = memo(SlowList);

function summarize(samples) {
  const updates = samples.filter((sample) => sample.phase === 'update');
  if (updates.length === 0) return { count: 0 };
  const durations = updates
    .map((sample) => sample.actualDuration)
    .sort((a, b) => a - b);
  return {
    count: durations.length,
    medianMs:
      (durations[Math.floor((durations.length - 1) / 2)] +
        durations[Math.floor(durations.length / 2)]) /
      2,
    p95Ms: durations[Math.ceil(durations.length * 0.95) - 1],
  };
}

function Case({ cached }) {
  'use no memo';
  const [tick, setTick] = useState(0);
  const [query, setQuery] = useState('');
  const samples = useRef([]);
  const List = cached ? MemoList : SlowList;
  const label = cached ? 'memo' : 'plain';

  function record(
    id,
    phase,
    actualDuration,
    baseDuration,
    startTime,
    commitTime,
  ) {
    samples.current.push({
      id,
      phase,
      actualDuration,
      baseDuration,
      startTime,
      commitTime,
    });
    if (samples.current.length > 200) samples.current.shift();
  }

  return (
    <section>
      <h2>{label}</h2>
      <label>
        查询
        <input value={query} onChange={(e) => setQuery(e.target.value)} />
      </label>
      <button onClick={() => setTick((value) => value + 1)}>
        无关状态加一
      </button>
      <button
        onClick={() => {
          samples.current = [];
        }}
      >
        清空样本
      </button>
      <button
        onClick={() => {
          console.table(samples.current);
          console.log(label, summarize(samples.current));
        }}
      >
        输出样本与统计
      </button>
      <Profiler id={label} onRender={record}>
        <span>无关状态：{tick}</span>
        <List query={query} />
      </Profiler>
    </section>
  );
}

export default function App() {
  return (
    <main>
      <Case cached={false} />
      <Case cached={true} />
    </main>
  );
}
```

这里故意只展示前 20 条，但仍对全部匹配项执行确定性的纯计算，用来隔离 render CPU 成本。
`slice(0, 20)` **不是虚拟列表**：没有滚动窗口、占位高度或完整数据导航，不能作为生产列表替代方案。
`use no memo` 仅用于实验隔离自动编译优化；未配置 Compiler 时是无害的字符串指令，手动 `memo` 仍有效。

### 测量步骤与指标边界

1. 在开发构建或专用 profiling 构建打开实验；普通生产构建默认禁用 Profiler 计时。
2. 记录 React 版本、浏览器、硬件、CPU 降速档位、StrictMode 与 Compiler 状态，保持两组一致。
3. 两组各预热数次，再分别点“清空样本”；查询都保持空字符串。
4. 两组交替、逐次点击“无关状态加一”至少 20 次，等待每次提交结束，不把多个更新人为批在一个事件里。
5. 最后输出样本，比较相同类型更新的中位数与 p95；小样本 p95 波动很大，重复多轮并保留原始记录。
6. 再清空样本并改变 query，观察 memo 不能跳过相关 props 更新。不要把两种交互混入同一统计。

实验的预期是：无关更新时，memo 组可以跳过 `SlowList`；查询变化时两组都需计算。
**这只是可验证的假设，不是本文已经测得的加速结果。** 不预填毫秒数、百分比或“必定跟手”的结论。

| 字段或工具              | 表示什么                                                  | 不能据此断言什么                                   |
| ----------------------- | --------------------------------------------------------- | -------------------------------------------------- |
| actualDuration          | 本次提交对应的被测子树 render 耗时                        | 不是完整交互延迟，也不包含全部 layout / paint      |
| baseDuration            | 根据近期各组件渲染成本估算的整棵子树重渲染成本            | 不是另一组真实基线实测，更不是固定不变的时间       |
| startTime / commitTime  | 开始渲染与提交的时间戳，可用 commitTime 对齐多处 Profiler | commitTime 不是提交耗时，二者差值也不是纯 CPU 耗时 |
| React DevTools Profiler | 定位昂贵组件及哪些提交触发它们                            | 不能替代浏览器对长任务和呈现延迟的分析             |
| 浏览器 Performance      | 检查事件处理、长任务、样式、layout、paint 等              | 单次本地记录不是线上用户的 INP 分布                |

`record` 只向有上限的 ref 缓冲区追加，不在提交回调里 `setState`，避免测量本身制造更新循环。
控制台输出放在单独按钮中，避免每次提交的日志污染对照。
首次 mount、开发 StrictMode 的额外检查和热更新不能与稳定的 update 样本混用。
需要解释真实用户“卡顿”时，应把 Profiler 的 render 数据和浏览器 Performance 录制放在一起看。

## 六、总结

先确认瓶颈属于组件计算、更新传播、宿主提交还是浏览器布局绘制，再只改变一个变量做前后对照。
本篇保留了列表优化方案，并提供独立可复现的 memo 测量实验；两者的证据边界不同，不能用后者替前者编造结果。
