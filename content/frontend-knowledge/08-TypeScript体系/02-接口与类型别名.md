# 接口与类型别名

## 一、是什么

**`interface`（接口）与 `type`（类型别名）是 TypeScript 中定义「命名类型」的两种语法。** 二者都能给对象、函数、数组等结构起名字并复用，能力高度重叠——很多场景下可以互换，因此「用哪个」是 TS 社区经久不衰的争论。

```ts
// 用 interface 描述一个用户对象
interface User {
  id: number;
  name: string;
}

// 用 type 描述同一个对象——结构完全等价
type User = {
  id: number;
  name: string;
};

const u: User = { id: 1, name: 'Tom' }; // 两者都能这样用
```

真正拉开差距的，是各自的**独占能力**：`interface` 有「声明合并」与「继承」，`type` 能表达「联合、交叉、字面量、映射、条件」类型。理解这些差异，才能做出正确的选型。

## 二、为什么

给类型「起名字」看似小事，实则是大型工程的基石：

- **复用**：一处定义、多处引用，避免重复的对象字面量类型散落各处。
- **契约**：`interface` 是模块间、前后端之间的显式数据结构约定。
- **可读性**：`function save(u: User)` 远胜 `function save(u: { id: number; name: string; email: string; ... })`。
- **可维护**：字段变更只改一处，所有引用点自动获得新形状，配合类型检查即时暴露受影响代码。

> 一句话：命名类型把「结构」抽象成「概念」。而 `interface`/`type` 就是给概念命名的两支笔——笔锋不同，适用场景也不同。

## 三、核心原理

### 1. interface：描述「对象形状」，可扩展、可合并

`interface` 的两大独占特性：

**① 继承（extends）**——语义清晰，可同时继承多个：

```ts
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): void;
}
// Dog = { name: string; bark(): void }
```

**② 声明合并（Declaration Merging）**——**同名 interface 会自动合并成员**，这是 `type` 完全没有的能力：

```ts
interface Config {
  host: string;
}
interface Config {
  port: number; // 与上面的 Config 自动合并
}
// 最终 Config = { host: string; port: number }
```

声明合并的典型用途：**给第三方库/全局对象「打补丁」**。例如扩展 `Express.Request`、`Window`、或给库的类型追加字段：

```ts
// 扩展全局 Window，追加自定义属性
interface Window {
  myAnalytics?: { track: (e: string) => void };
}
```

### 2. type：表达「类型的运算」，能力更广

`type` 是类型的**别名**，可以给任何类型起名，尤其擅长 `interface` 做不到的组合运算：

```ts
// ① 联合类型（interface 无法表达）
type Id = string | number;
type Status = 'pending' | 'success' | 'error';

// ② 交叉类型（组合多个类型）
type Named = { name: string };
type Aged = { age: number };
type Person = Named & Aged; // { name: string; age: number }

// ③ 元组、基础类型别名
type Pair = [number, number];
type Callback = (err: Error | null) => void;

// ④ 映射类型 / 条件类型（详见《类型体操》）
type Keys = keyof Person; // 'name' | 'age'
type ReadOnlyPerson = Readonly<Person>;
```

**关键区别：`type` 不会声明合并。** 重复定义同名 `type` 直接报错，而重复 `interface` 会合并——这既是 `interface` 的优势（可扩展），也是它的风险（可能被意外合并）。

### 3. extends vs & ：继承与交叉的微妙差异

两者都能「组合类型」，但行为不同：

```text
                    interface B extends A     type B = A & {...}
冲突成员            编译期报错（要求兼容）     得到 never（交叉不兼容类型）
性能                命名清晰、报错友好         大型交叉类型可能变慢、报错晦涩
适用                面向对象的「是一种」       函数式的「类型运算/组合」
```

```ts
interface A {
  x: string;
}

// extends：若冲突，TS 会明确报错指出哪个成员不兼容
interface B extends A {
  x: string;
  y: number;
} // ✅

// &：冲突成员会被「交叉」，string & number = never
type C = A & { x: number }; // C['x'] 变成 never（静默，易埋坑）
```

### 4. 二者能力对照表

| 能力                     | interface |      type      |
| ------------------------ | :-------: | :------------: |
| 描述对象/类形状          |    ✅     |       ✅       |
| 继承/扩展（extends）     |    ✅     |     ✅(&)      |
| **声明合并**             |    ✅     |       ❌       |
| 联合类型（`A \| B`）     |    ❌     |       ✅       |
| 交叉类型（`A & B`）      | (extends) |       ✅       |
| 字面量类型别名           |    ❌     |       ✅       |
| 映射/条件类型            |    ❌     |       ✅       |
| 元组、基础类型别名       |    ❌     |       ✅       |
| `implements`（被类实现） |    ✅     | ✅(需对象类型) |

## 四、实践

### 1. 选型约定（团队主流共识）

- **对象的形状、需要被 `implements`/继承、可能要扩展的公共契约** → 用 `interface`。
- **联合、交叉、字面量、工具类型、映射/条件类型、元组、函数签名别名** → 用 `type`。
- **拿不准时**：对象结构优先 `interface`（报错更友好、可扩展），其余用 `type`。团队内**保持一致**比「选对」更重要。

```ts
// ✅ 对象契约用 interface
interface PostProps {
  title: string;
  tags: string[];
}

// ✅ 联合/工具类型用 type
type Theme = 'light' | 'dark';
type PostPreview = Pick<PostProps, 'title'>;
type Result<T> = { ok: true; data: T } | { ok: false; error: string };
```

### 2. 用可辨识联合表达「状态机」

`type` 的联合 + 字面量是建模「互斥状态」的利器，配合 `switch` 收窄获得穷尽检查：

```ts
type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: string }
  | { status: 'error'; message: string };

function render(s: RequestState) {
  switch (s.status) {
    case 'idle':
      return '待发起';
    case 'loading':
      return '加载中…';
    case 'success':
      return s.data; // 自动收窄出 data
    case 'error':
      return s.message; // 自动收窄出 message
    // 漏写分支时，s 会是 never，可加 default 做穷尽断言
  }
}
```

### 3. 函数类型：两种写法都常见

```ts
interface Fn {
  (a: number): number;
} // 调用签名写法
type Fn2 = (a: number) => number; // 箭头写法（更常用、更简洁）
```

## 五、常见误区

- **误区一：`interface` 一定比 `type` 快、一定更好。** 早年确有性能差异，现代 TS 编译器对两者优化已趋同；选型应看**语义与能力需求**，而非性能传闻。
- **误区二：以为 `type` 也能声明合并。** `type` 重名直接报错。需要「被扩展/打补丁」的全局或库类型，必须用 `interface`。
- **误区三：用 `&` 交叉时忽视冲突成员变 `never`。** `A & { x: number }` 若 `A.x` 是 `string`，结果 `x: never` 且**静默通过**，比 `extends` 的显式报错更危险。
- **误区四：滥用声明合并。** 同名 `interface` 自动合并虽强大，但分散在多文件的合并会让类型「来历不明」，除扩展第三方/全局类型外应谨慎。
- **误区五：所有类型都用 `interface` 硬套。** 联合、字面量、工具类型本质是 `type` 的领域，强行用 `interface` 无法表达，反而绕弯。

## 六、总结

- `interface` 与 `type` 能力高度重叠，**对象形状、继承、声明合并**是 `interface` 的主场；**联合、交叉、字面量、映射、条件类型**是 `type` 的领域。
- **声明合并**是 `interface` 独有、`type` 没有的关键差异——扩展第三方/全局类型时必须用它。
- `extends` 冲突显式报错、`&` 冲突静默变 `never`，组合类型时优先 `extends` 更安全。
- 选型经验：**对象契约优先 `interface`，类型运算用 `type`，团队内保持一致**。
- 二者都是编译期概念，运行时同样被擦除（见《类型系统基础》）。

> `interface` 与 `type` 之争，本质是**「面向对象式的声明扩展」**与**「函数式式的类型运算」**两种心智的分野。真正成熟的团队不会站队，而是按语义各取所长——**让类型的写法，如实反映它的意图。**
