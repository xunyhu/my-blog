# TS工程配置

## 一、是什么

**`tsconfig.json` 是一个 TypeScript 项目（工程）的「总配置文件」。** 一个目录下存在 `tsconfig.json`，就标志着「这里是一个 TS 项目」；它规定了：编译成什么版本的 JS、用哪种模块系统、类型检查有多严、哪些文件纳入编译。

本项目根目录的 `tsconfig.json` 就是一个典型样本：

```jsonc
// tsconfig.json（本博客项目真实配置，节选）
{
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "strict": true,
    "noEmit": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "incremental": true,
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./*"] },
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts"],
  "exclude": ["node_modules"],
}
```

理解这份配置，就理解了「TS 如何融入一个现代 Next.js 工程」。

## 二、为什么

- **一致性**：全项目统一的编译与检查标准，避免各文件行为不一。
- **正确性**：`strict` 等选项决定了类型检查的严格度——配置松，类型形同虚设。
- **工具链协同**：编辑器、`tsc`、打包器（Next/Turbopack）、CI 都读同一份 tsconfig，配置即「单一事实源」。
- **性能**：`incremental`、`include/exclude` 影响编译速度与范围。

> 本项目的 pre-commit 钩子执行 `npx tsc --noEmit` 做类型门禁——它读的就是这份 tsconfig。配置的严格程度，直接决定了这道门禁的强度。

## 三、核心原理

### 1. compilerOptions：编译产物的「形状」

```text
   target   →  编译成哪个 ES 版本的 JS（语法降级目标）
   module   →  用哪种模块系统（esnext / commonjs / nodenext）
   lib      →  可用的内置类型库声明（dom / esnext / webworker…）
```

- **`target: "ES2017"`**：产物语法降到 ES2017（如 async/await 保留，更新语法转译）。Next.js 会按浏览器支持再处理，故这里不必设太低。
- **`lib: ["dom", "dom.iterable", "esnext"]`**：告诉 TS「运行环境有 DOM API 和最新 ES 特性类型」。写前端必须有 `dom`，否则 `document`/`window` 无类型。
- **`module: "esnext"` + `moduleResolution: "bundler"`**：用最新 ESM 语法，模块解析交给打包器（见下）。

**`target` 与 `lib` 的区别**常被混淆：`target` 决定**语法降级到哪**，`lib` 决定**有哪些 API 类型可用**——前者是输出，后者是输入环境。

### 2. strict 族：类型检查的严格度

`strict: true` 是个「总开关」，一次性打开一组严格检查：

```jsonc
{
  "compilerOptions": {
    "strict": true, // 打开下面全部
    // 等价于同时开启：
    // "strictNullChecks": true,        ← 最重要：null/undefined 必须显式处理
    // "strictFunctionTypes": true,     ← 函数参数逆变检查
    // "strictBindCallApply": true,
    // "strictPropertyInitialization": true, // 类属性必须初始化
    // "noImplicitAny": true,           ← 禁止隐式 any
    // "noImplicitThis": true,
    // "alwaysStrict": true,
    // "useUnknownInCatchVariables": true // catch(e) 的 e 是 unknown
  },
}
```

新项目**务必从第一天就 `strict: true`**；老项目渐进迁移时，可先开 `noImplicitAny`、再开 `strictNullChecks`。

**推荐再加的严格选项**（不在 `strict` 内）：

```jsonc
{
  "noUncheckedIndexedAccess": true, // arr[i] / obj[k] 结果含 undefined，防越界
  "noImplicitOverride": true, // 子类覆写必须写 override
  "noFallthroughCasesInSwitch": true, // switch 禁止穿透
  "exactOptionalPropertyTypes": true, // 区分「未传」与「传 undefined」（较激进）
}
```

### 3. moduleResolution：模块如何被找到

这是近年变化最大、最易踩坑的选项：

| 取值       | 场景                                | 说明                                            |
| ---------- | ----------------------------------- | ----------------------------------------------- |
| `bundler`  | 用打包器（Next/Vite/webpack）的项目 | TS 5.0+ 推荐，支持 `exports` 字段、无需写扩展名 |
| `nodenext` | 纯 Node（含 ESM/CJS 混合）库或服务  | 严格遵循 Node 的 ESM 规则，需写全扩展名         |
| `node16`   | 对齐 Node 16 的解析                 | 与 nodenext 类似                                |
| `node`(旧) | 遗留 CommonJS                       | 已不推荐                                        |

本项目是 Next.js（有打包器），故用 **`bundler`**——这也是绝大多数前端应用的正确选择。若是发布到 npm 的纯 Node 库，则应用 `nodenext` 以严格匹配 Node 的解析。

### 4. paths：路径别名

`paths` 让你用别名代替冗长的相对路径，告别 `../../../`：

```jsonc
{
  "compilerOptions": {
    // "baseUrl": ".",   // TS 5+ 中 paths 用相对 tsconfig 的路径，baseUrl 可省
    "paths": {
      "@/*": ["./*"], // @/ 映射到项目根
    },
  },
}
```

于是本项目里可以写 `import type { Tag } from '@/types/blog'`，而非 `../../types/blog`。

```text
   "@/types/blog"
    │  └──────┬───────┘
    │      匹配 @/* 的 * 部分 = "types/blog"
    └─ 前缀 @/ 映射到 "./*"（根目录）
    结果：解析为 <root>/types/blog
```

⚠️ **`paths` 只影响 TS 类型解析，不影响运行时打包**。运行时能否解析，取决于打包器（Next.js 会自动读取 tsconfig 的 `paths`，故无需额外配置；纯 tsc 场景需配 `tsconfig-paths` 等）。

### 5. include / exclude / files：编译范围

```jsonc
{
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts"],
  "exclude": ["node_modules"],
}
```

- **`include`**：纳入编译的文件 glob。`**/*.ts(x)` 覆盖全部 TS 源文件；`.next/types/**` 是 Next.js 自动生成的路由类型。
- **`exclude`**：从 include 中排除。`node_modules` 默认排除。
- **`files`**：精确列出文件（与 include 二选一，少用）。

范围过大拖慢编译、过小则漏检——精确的 `include` 是编译性能与覆盖率的关键。

### 6. isolatedModules 与 Next.js 专用项

```jsonc
{
  "isolatedModules": true, // 每个文件可被单独转译（Babel/esbuild/Turbopack 要求）
  "esModuleInterop": true, // 兼容 CommonJS 默认导入（import x from 'cjs-pkg'）
  "resolveJsonModule": true, // 允许 import json
  "jsx": "react-jsx", // 用 React 17+ 的自动 JSX 运行时（无需 import React）
  "noEmit": true, // 不产出 JS（交给 Next 打包，tsc 只做类型检查）
  "incremental": true, // 增量编译，缓存到 .tsbuildinfo 加速
  "plugins": [{ "name": "next" }], // Next.js 的 TS 语言服务插件（路由类型增强）
}
```

- **`isolatedModules: true`** 是现代打包器（逐文件转译）的必备项，它禁用一些「跨文件才能正确处理」的语法（如 `const enum`、`export` 纯类型需用 `export type`）。
- **`noEmit: true`** 揭示了一个真相：**Next.js 项目里 `tsc` 不负责产出 JS，只做类型检查**——真正的编译由 Next 的打包器（Turbopack/webpack）完成。这也是为什么 `tsc --noEmit` 能当类型门禁。
- **`jsx: "react-jsx"`** 用 React 17+ 的自动运行时，写 JSX 不再需要 `import React`。

### 7. 项目引用（Project References）：大型 monorepo

超大项目可拆成多个子项目，用 `references` + `composite` 增量构建、复用产物：

```jsonc
// 根 tsconfig.json
{
  "references": [{ "path": "./packages/ui" }, { "path": "./packages/api" }],
  "files": [],
}
// 子项目 tsconfig 需开启 "composite": true
```

`composite` 让子项目可被独立、增量地构建并缓存，配合 `tsc --build` 实现 monorepo 的高效类型检查。

## 四、实践：分层配置

大型项目常用 `extends` 分层，共享基础配置：

```jsonc
// tsconfig.base.json —— 团队共享的严格基线
{ "compilerOptions": { "strict": true, "target": "ES2020", "moduleResolution": "bundler" } }

// tsconfig.json —— 项目特有配置继承基线
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": { "paths": { "@/*": ["./*"] } },
  "include": ["src"]
}
```

本项目虽是单包，但配置已体现「Next.js 最佳实践基线」：`strict` + `bundler` + `paths` + `noEmit` + Next 插件。

## 五、常见误区

- **误区一：新项目不开 `strict`，事后补。** 越晚开越痛（要修的历史 `any`/null 越多）。**第一天就 `strict: true`**。
- **误区二：以为改了 `paths` 运行时就能解析。** `paths` 只管类型解析；运行时依赖打包器支持（Next 会读，裸 Node 需额外工具）。
- **误区三：`target` 设太低（如 ES5）拖累现代特性。** 前端有打包器兜底，`target` 可设较新；纯 Node 按运行版本设。
- **误区四：混淆 `target` 与 `lib`。** `target` 是输出语法版本，`lib` 是可用 API 类型；改 `lib` 不会降级语法。
- **误区五：`moduleResolution` 用错。** 打包器项目用 `bundler`，纯 Node 库用 `nodenext`；用错会导致解析行为与运行时不一致。
- **误区六：`noEmit` 以为没用。** 在 Next 项目里它正是「tsc 只检查不产出」的关键，让类型检查与打包解耦。

## 六、总结

- `tsconfig.json` 是 TS 工程的总控台，规定**编译目标、模块系统、严格度、文件范围**。
- `compilerOptions` 中：`target`/`lib` 定输出与环境类型，`module`/`moduleResolution` 定模块与解析策略（打包器项目用 `bundler`），`paths` 定路径别名。
- **`strict: true` 是底线**，可再加 `noUncheckedIndexedAccess` 等强化；新项目务必从第一天开启。
- `include/exclude` 控编译范围；`isolatedModules`/`noEmit`/`jsx`/Next 插件适配现代打包器工作流。
- 大型项目用 `extends` 分层共享基线、`references`+`composite` 做 monorepo 增量构建。
- 本项目 tsconfig 是「Next.js + TS 严格模式」的标准范式，也是其 pre-commit 类型门禁的依据。

> `tsconfig.json` 常被当作「脚手架生成后就不再看」的文件，但它其实是**项目类型安全的第一道防线**：一个 `strict: true`，决定了后面所有类型标注是「认真的契约」还是「摆设的注释」。读懂并主动调校它，是从「会写 TS」走向「会治理 TS 工程」的必经一步。
