# 类型系统基础

## 一、是什么

**TypeScript 是 JavaScript 的「静态类型超集」**：它包含 JS 的全部语法，并在其上加了一层**编译期类型系统**；编译（`tsc` 或打包器的 transpile）后类型被擦除，产物就是普通 JS。

```text
   你写的 .ts/.tsx                     浏览器/Node 运行的 .js
┌──────────────────────┐   tsc/esbuild  ┌──────────────────────┐
│ let n: number = 1;    │ ─────────────▶ │ let n = 1;            │
│ function f(x: string) │   类型检查 +    │ function f(x) { … }   │
│   { … }               │   类型擦除      │                       │
└──────────────────────┘                └──────────────────────┘
        ↑ 编译期：报错、补全、重构              ↑ 运行期：没有类型
```

理解 TS 类型系统，要抓住三块基石：**结构类型（如何判定类型相等）**、**类型擦除（类型只活在编译期）**、**类型层级（谁是谁的子类型）**。

## 二、为什么

JavaScript 是动态弱类型，很多错误只在运行时暴露。TS 的静态类型带来四类确定性收益：

- **编译期拦截错误**：拼写错字段、传错参数类型、访问 `null` 的属性——在保存/构建时即报错，而非上线后崩溃。
- **编辑器智能提示**：类型即文档，自动补全、跳转定义、参数提示大幅提升效率。
- **重构安全网**：改一个接口字段，所有受影响处立即标红，大型项目尤其关键。
- **团队协作契约**：函数签名、接口定义就是模块间的显式契约。

> 本项目（Next.js + React）全程 TypeScript，`tsconfig.json` 开启 `strict`，pre-commit 钩子跑 `tsc --noEmit` 做类型门禁——这正是「类型即质量护栏」的落地。

## 三、核心原理

### 1. 结构类型系统（Structural Typing）

TS 判定「A 是否能赋给 B」，看的不是名字/声明来源，而是**结构是否兼容**——即「A 是否具备 B 要求的全部成员」。这就是俗称的**鸭子类型**：

```ts
interface Point { x: number; y: number }

const p = { x: 1, y: 2, z: 3 }; // 多了一个 z
const pt: Point = p;            // ✅ 合法：p 具备 Point 要求的 x、y
```

```text
结构兼容判定：  目标类型 Point 需要 { x, y }
                源类型 p 提供 { x, y, z } ⊇ { x, y }  →  兼容 ✅

对比「名义类型」（如 Java/C#）：必须显式 implements/继承同名类型才算数
```

结构类型让 TS 能无缝给「既有的、非为 TS 设计的」JS 代码加类型，但也埋下「意外兼容」的坑（见常见误区）。

### 2. 类型擦除（Type Erasure）

类型只存在于编译期，运行时**没有任何类型信息**。这带来两条铁律：

- **不能依赖类型做运行时判断**：`if (x instanceof MyInterface)` 非法（接口不存在于运行时）；运行时的类型判断要靠 `typeof`/`instanceof`/自定义守卫。
- **TS 不会校验外部数据**：`JSON.parse`、接口响应、`process.env` 拿到的值，TS 只能按你「声明」的类型对待，运行时是否真的如此它管不了——需要用 zod/valibot 等做运行时校验。

```ts
// ❌ 误以为有运行时保护
function parse(raw: string): User { return JSON.parse(raw); } // 实际可能是任何东西

// ✅ 运行时校验（zod 示例思路）
const User = z.object({ id: z.string(), name: z.string() });
const user = User.parse(JSON.parse(raw)); // 运行时真正校验
```

### 3. 类型层级：any / unknown / never / void

这四个「特殊类型」定义了类型系统的上下边界：

```text
        any ─── 逃逸舱：既是所有类型的父类也是子类，关闭一切检查（应尽量禁用）
         │
      unknown ── 顶层类型（top type）：任何值都可赋给它，但用它前必须先收窄
         │
   ┌─────┴───── 所有具体类型（string/number/对象/联合…）
         │
       never ─── 底层类型（bottom type）：不可能的值（抛异常、穷尽检查、永不返回）
```

| 类型      | 含义                       | 能赋值给它 | 用它时的限制           |
| --------- | -------------------------- | ---------- | ---------------------- |
| `any`     | 放弃类型检查               | 任何值     | 无（危险）             |
| `unknown` | 未知但安全的顶层类型       | 任何值     | 必须先收窄才能操作     |
| `never`   | 永不存在的值               | 无         | 用于穷尽性/异常        |
| `void`    | 函数无返回值               | `undefined`| —                      |

`unknown` 是 `any` 的「类型安全版」：接收任意输入（如 `catch (e)`、`JSON.parse`）时首选它，强制你在使用前收窄：

```ts
function handleError(err: unknown) {
  // err.message;            // ❌ 报错：unknown 不能直接访问属性
  if (err instanceof Error) {
    console.error(err.message); // ✅ 收窄后可用
  }
}
```

### 4. 联合、交叉与字面量类型

```ts
type Id = string | number;         // 联合：是其中之一
type Admin = { role: 'admin' } & { name: string }; // 交叉：同时满足
type Dir = 'up' | 'down';          // 字面量联合：取值被限定
```

字面量类型 + 联合是 TS 表达「有限枚举」的利器，比 `enum` 更轻量、更可 tree-shake（现代项目常优先用字面量联合而非 `enum`）。

### 5. 严格模式（strict）

`tsconfig.json` 的 `strict: true` 会打开一组严格检查，其中最重要的是 **`strictNullChecks`**：`null`/`undefined` 不再能随意赋给其他类型，从根源消灭「Cannot read property of undefined」这类运行时崩溃。

```jsonc
{
  "compilerOptions": {
    "strict": true,          // 一键开启全部严格检查
    "noUncheckedIndexedAccess": true // 索引访问结果含 undefined，更安全
  }
}
```

## 四、实践

### 1. 类型收窄（Narrowing）

在 `unknown`/联合类型上，用控制流把类型「收窄」到具体分支，是 TS 日常最高频的操作：

```ts
function format(value: string | number | null) {
  if (value === null) return 'N/A';       // 收窄掉 null
  if (typeof value === 'string') return value.trim();  // 收窄为 string
  return value.toFixed(2);                 // 此处只剩 number
}
```

常用收窄手段：`typeof`、`instanceof`、`in`、字面量比较、真值判断、以及**自定义类型守卫**：

```ts
interface Cat { meow(): void }
interface Dog { bark(): void }
function isCat(a: Cat | Dog): a is Cat {   // 类型谓词
  return (a as Cat).meow !== undefined;
}
```

### 2. 标注 vs 推导的取舍

- 变量初始化时能推导就**别手写标注**（`const n = 1` 已推为 `number`）；
- 函数**参数与返回值**应显式标注（这是对外契约，也防止推导意外）；
- 详见本模块《类型推导》。

## 五、常见误区

- **误区一：`any` 能过编译就是对的。** `any` 会「传染」——一个 `any` 流入，下游检查全部失效。应优先 `unknown` + 收窄，或用 `@typescript-eslint/no-explicit-any` 拦截。
- **误区二：TS 类型能防住运行时脏数据。** 类型在运行时已被擦除，接口/`JSON.parse`/环境变量都需运行时校验（zod 等），不能只靠类型断言。
- **误区三：结构类型「方便」就随便赋值。** 结构兼容会导致「意外通过」，如 `{ x:1, y:2, z:3 }` 能赋给 `Point`；对需要「名义区分」的场景（如 `UserId` vs `OrderId`），可用**品牌类型（branded type）** 人为制造不兼容。
- **误区四：`null` 和 `undefined` 可互换。** 开启 `strictNullChecks` 后二者都必须显式处理；用可选链 `?.` 与空值合并 `??` 安全访问。
- **误区五：把 `type`/`interface` 当运行时对象用。** 它们编译后消失，不能 `typeof SomeInterface` 做运行时判断。

## 六、总结

- TS 是 JS 的**静态类型超集**，类型只活在编译期，**编译后被完全擦除**。
- 判定类型兼容靠**结构类型系统**（鸭子类型），而非名义——好处是能包裹既有 JS，代价是可能「意外兼容」。
- 类型层级中，`unknown`（安全的顶层）应取代 `any`（危险的逃逸舱），`never` 表达不可能，用于穷尽性检查。
- **严格模式（尤其 `strictNullChecks`）** 是类型价值的底线；配合**类型收窄**处理联合与 `unknown`。
- 类型不等于运行时安全：外部数据一律走运行时校验。

> TS 类型系统的心智可以浓缩成一句话：**「用编译期的结构契约，换取运行期之前就发现问题」**——但永远记得，类型会在编译后消失，运行时的世界仍需运行时的手段来守护。
