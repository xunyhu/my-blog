# 浏览器缓存

## 一、是什么

HTTP 缓存保存请求对应的响应，在满足复用条件时避免重复下载或重复生成内容。
浏览器私有缓存只服务当前客户端，共享缓存则可能服务多个用户，例如 CDN 与反向代理。

“强缓存”和“协商缓存”是常用教学分类：前者直接复用新鲜响应，后者通过条件请求验证已有表示。
更准确的判断顺序是：是否允许存储、是否匹配变体、是否新鲜、是否允许复用、是否需要验证。

缓存是性能机制，也是数据隔离机制。
把用户 A 的响应缓存成公共内容，比“页面更新慢”严重得多。

## 二、为什么

有效缓存减少 RTT、流量和源站计算，尤其适用于版本化的 JS、CSS、图片。
但缓存策略必须跟随资源变化方式，而不是给所有响应复制同一组头部。

| 资源                       | 常见目标               | 基础策略                   |
| -------------------------- | ---------------------- | -------------------------- |
| 带内容 hash 的公开静态文件 | 同一 URL 内容不变      | 长 max-age 与 immutable    |
| 经常更新的公开 HTML        | 发布及时生效           | no-cache 与验证器          |
| 普通个性化页面             | 不跨用户共享且及时更新 | private, no-cache          |
| 令牌、账单等敏感响应       | 不落入 HTTP 缓存       | no-store，并审查其他存储层 |

这里是策略起点，不是对任何 CDN 产品的无条件保证。
实际生效值可能被代理、平台规则或 Service Worker 覆盖，必须验证最终响应与实际复用路径。

## 三、核心原理

### 多层缓存不是固定串行队列

```text
页面请求
  |
  +-- Service Worker fetch 处理器（若已控制页面）
  |      +-- Cache Storage 命中 -> 返回自定义响应
  |      +-- fetch -> 浏览器 HTTP 缓存或网络
  |
  +-- 浏览器 HTTP 缓存（内存或磁盘实现细节）
         +-- 可直接复用 -> 返回
         +-- 验证或未命中 -> CDN -> 网关 -> 源站

bfcache: 恢复整页与 JS 状态，不等于重新发起上述请求
```

Service Worker 的 Cache Storage 是脚本管理的存储，不会自动按 HTTP Cache-Control 过期。
如果代码无条件 `cache.put()`，即使响应有 no-store，也不能假定脚本就不存它。
不要缓存登录令牌或敏感接口；离线策略也要区分公开资源与用户数据。

bfcache 是页面快照恢复，不能仅靠 no-cache 假定后退一定重新验证。
登录态变化应在页面恢复时重新核验权限，服务端始终是最终授权边界。

### Cache-Control 的指令语义

| 指令                     | 含义                             | 容易误读的边界                   |
| ------------------------ | -------------------------------- | -------------------------------- |
| max-age=N                | 响应新鲜寿命，单位秒             | 不是承诺一定保存 N 秒            |
| s-maxage=N               | 共享缓存的新鲜寿命               | 浏览器私有缓存不按它计时         |
| no-cache                 | 复用前必须成功验证               | 可以存储，不是禁止缓存           |
| no-store                 | 不存储本次请求或响应的缓存副本   | 不自动清除旧缓存、日志或应用存储 |
| private                  | 不允许共享缓存存储               | 不表示加密，也不等于永不过期     |
| public                   | 显式允许共享缓存存储             | 不能给个性化响应随意添加         |
| must-revalidate          | 过期后必须验证成功才能复用       | 不是每次请求都回源               |
| immutable                | 新鲜期间表示内容不会改变         | 应配合内容版本化 URL             |
| stale-while-revalidate=N | 允许指定窗口内先用旧值再后台验证 | 需要支持该扩展的缓存             |
| stale-if-error=N         | 特定错误时允许有限期使用旧响应   | 不适合要求绝对实时的业务         |
| no-transform             | 请求中间层不要变换表示           | 不负责禁止缓存                   |

max-age 的年龄判断会考虑 Date、Age、传输时间和本地驻留时间。
例如 CDN 响应已带 `Age: 50`，`max-age=60` 不代表到浏览器后又获得完整 60 秒。
同时存在时，max-age 优先于 Expires；共享缓存还需考虑 s-maxage。
没有 Cache-Control 不等于不缓存，某些响应会进入启发式缓存。

### 条件验证与 304

```text
第一次: GET /article -> 200 + ETag: "v1" + 正文
                           |
                           v
                       保存表示

再次复用前: If-None-Match: "v1"
             |
             +-- 未变化 -> 304 + 更新后的缓存元数据 -> 复用旧正文
             +-- 已变化 -> 200 + ETag: "v2" + 新正文
```

ETag 是不透明的表示验证器，不必是文件 hash，但生成方式必须稳定并反映所选表示。
强 ETag 表示字节级一致，弱 ETag 形如 `W/"v1"`，表达语义等价。
GET、HEAD 的 If-None-Match 使用弱比较；范围请求等场景可能需要强验证器。

Last-Modified 对应 If-Modified-Since，受秒级精度与时间可靠性限制。
两种条件同时出现时，If-None-Match 优先，不能因日期条件成立就忽略不匹配的 ETag。
304 不携带响应正文，但仍需要正确返回适用的 ETag、Cache-Control、Vary 等元数据。
浏览器内部完成验证时，JavaScript fetch 通常拿到合并后的响应，而不是裸 304。

### 缓存键与隐私边界

同一个 URL 可能按 Accept-Language 或 Accept-Encoding 返回不同表示。
`Vary` 声明哪些请求首部参与变体选择，例如 `Vary: Accept-Encoding`。
动态 CORS 响应还需要 `Vary: Origin`，否则 CDN 可能把某个来源的许可头发给其他来源。

Cookie 的存在不会自动保证响应私有，Set-Cookie 也不是通用的“禁止 CDN 缓存”开关。
不能用 `Vary: Cookie` 代替对个性化响应明确设置 private 或 no-store。
带 Authorization 的响应有额外共享缓存限制，但 public、s-maxage 等显式规则可能改变可缓存性，务必审查。

这些原则与 [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching) 和 [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html) 一致。

## 四、代码实现

### 无服务器的缓存验证器实验

保存为 `cache-demo.mjs`，使用 Node.js 22+ 执行 `node cache-demo.mjs`。
数据、请求和响应都在内存中，无隐藏接口，也不模拟浏览器完整缓存实现。
ETag 使用本例单一表示的 SHA-256；示例支持通配符、弱标签和多个条件标签。

```js
import assert from 'node:assert/strict';
import { createHash } from 'node:crypto';

const body = JSON.stringify({ title: '缓存实验', version: 1 });
const etag = `"${createHash('sha256').update(body).digest('hex')}"`;
const modified = 'Fri, 02 Oct 2026 00:00:00 GMT';

function respond(request) {
  const url = new URL(request.url);
  if (url.pathname === '/secret') {
    return new Response('sensitive demo', {
      headers: { 'Cache-Control': 'no-store' },
    });
  }
  if (!['GET', 'HEAD'].includes(request.method)) {
    return new Response(null, { status: 405, headers: { Allow: 'GET, HEAD' } });
  }
  const headers = {
    ETag: etag,
    'Last-Modified': modified,
    'Cache-Control': 'private, no-cache',
    'Content-Type': 'application/json; charset=utf-8',
  };
  const condition = request.headers.get('if-none-match');
  const since = request.headers.get('if-modified-since');
  let unchanged = false;
  if (condition !== null) {
    // 标签中的逗号不能作为普通 split(',') 的分隔依据。
    const tags = condition.match(/(?:W\/)?"[^"\r\n]*"/g) ?? [];
    unchanged =
      condition.trim() === '*' ||
      tags.some((tag) => tag.replace(/^W\//, '') === etag);
  } else if (since !== null) {
    const timestamp = Date.parse(since);
    unchanged = Number.isFinite(timestamp) && timestamp >= Date.parse(modified);
  }
  if (unchanged) return new Response(null, { status: 304, headers });
  return new Response(request.method === 'HEAD' ? null : body, { headers });
}

const request = (headers = {}, path = '/article') =>
  new Request(`https://demo.test${path}`, { headers });
const first = respond(request());
assert.equal(first.status, 200);
assert.equal(await first.text(), body);

const weak = respond(request({ 'If-None-Match': `"other", W/${etag}` }));
assert.equal(weak.status, 304);
assert.equal(await weak.text(), '');
assert.equal(weak.headers.get('etag'), etag);
assert.equal(respond(request({ 'If-None-Match': '*' })).status, 304);
assert.equal(respond(request({ 'If-Modified-Since': modified })).status, 304);
assert.equal(respond(request({ 'If-Modified-Since': 'invalid' })).status, 200);

// ETag 不匹配时，即使日期相等也必须返回新表示。
assert.equal(
  respond(
    request({
      'If-None-Match': '"old"',
      'If-Modified-Since': modified,
    }),
  ).status,
  200,
);
assert.equal(
  respond(request({}, '/secret')).headers.get('cache-control'),
  'no-store',
);
console.log('200, 304, validator precedence and no-store: passed');
```

这里的 `/secret` 只演示缓存头，不提供真实鉴权。
生产实现还需要完整路由、认证、条件首部语法校验，以及压缩变体与 ETag 的一致性管理。

## 五、工程实践

### 排查发布后仍显示旧版本

1. 记录响应来源：memory cache、disk cache、Service Worker、CDN 命中还是源站。
2. 同时记录 URL、ETag、Age、Cache-Control、Vary 和部署版本，不只截图页面。
3. 确认 HTML 是否仍指向旧 hash；资源更新却 URL 不变时，长缓存无法及时失效。
4. 检查 Service Worker 的版本更新、激活与 Cache Storage 清理策略。
5. 对 CDN 执行受控失效后再复测，不把“我本机清缓存好了”当作全网修复。
6. 回滚时保留旧 hash 资源，避免旧页面引用的脚本立即变成 404。

### 安全缓存头落地

以下分别是三种响应的头部示意，不要把它们合并为一个配置。

```http
Cache-Control: public, max-age=31536000, immutable
```

只用于确定不个性化、内容变更就换 URL 的公开静态资源。

```http
Cache-Control: private, no-cache
ETag: "profile-version-7"
```

用于允许浏览器保存但复用前需验证的个性化内容，验证前仍要检查当前用户身份。

```http
Cache-Control: no-store
```

用于敏感响应；还要确认网关没有强制缓存，应用没有写入 Cache Storage、localStorage 或日志。
如果旧版本曾允许公开缓存，只改新响应头不会召回所有旧副本，需要专门的失效与泄漏处置。

### 常见误区

- **304 比 200 永远更好**：304 仍有往返，直接复用新鲜响应才可能完全省网络。
- **no-cache 就不能存**：它约束复用前验证；no-store 才约束存储。
- **private 意味着数据绝对安全**：它只限制共享缓存，不替代鉴权或终端安全。
- **DevTools 禁用缓存就覆盖所有层**：Service Worker、CDN 与 bfcache 需要分别检查。
- **缓存时长到了副本立刻删除**：过期表示通常仍可用于验证，驱逐与新鲜度不同。

## 六、总结

缓存策略同时回答“谁可以存、能存多久、如何验证、如何隔离用户”。
优先让静态资源 URL 不可变，让动态表示可验证，让敏感内容不可被错误复用。
