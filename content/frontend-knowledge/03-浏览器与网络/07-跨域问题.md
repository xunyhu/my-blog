# 跨域问题

## 一、是什么

同源要求协议、主机和有效端口都相同。
同源策略限制不同来源脚本对资源与数据的访问，CORS 则允许服务器通过响应首部明确开放跨源读取。

同源不等于同站：同站判断主要涉及 scheme 与可注册域等规则，Cookie 的 SameSite 使用的是站点语义。
两个子域可以同站但跨源，同一主机不同端口也属于跨源。

| 页面与目标                                     | 同源吗 | 原因             |
| ---------------------------------------------- | ------ | ---------------- |
| https://a.example 与 https://a.example:443     | 是     | 默认有效端口相同 |
| http://a.example 与 https://a.example          | 否     | scheme 不同      |
| https://a.example 与 https://api.example       | 否     | 主机不同         |
| http://127.0.0.1:8080 与 http://127.0.0.1:8081 | 否     | 端口不同         |

CORS 不是防火墙，也不是服务端鉴权系统。
某些跨源请求会先发送，只是浏览器不把响应交给脚本；不能把“读取被阻止”理解为“服务器没有执行”。

## 二、为什么

典型场景是页面与 API 部署在不同源，需要携带登录 Cookie，并读取自定义响应头。
这涉及三层独立约束：

1. 浏览器是否允许发送该形式的请求。
2. 凭据是否符合发送条件。
3. 响应是否允许被当前页面脚本读取。

Node.js、命令行客户端不执行浏览器的 CORS 读取限制。
所以“命令行请求成功，但浏览器失败”并不矛盾，必须在浏览器里检查预检和实际响应。

## 三、核心原理

### 什么时候需要 OPTIONS

常见的免预检请求只使用 GET、HEAD、POST，且开发者设置的头部、值与请求体满足 CORS 安全列表规则。
例如符合约束的 text/plain POST 可以免预检；application/json、自定义 X-\* 首部或 Authorization 通常触发预检。
“GET 不预检、POST 必预检”都不成立，GET 加自定义头也可能预检。

```text
页面 origin A                               API origin B
  | -- OPTIONS /echo ------------------------> |
  |    Origin: A                               |
  |    Access-Control-Request-Method: POST      |
  |    Access-Control-Request-Headers:          |
  |      content-type,x-demo                    |
  | <--- 204 + 许可 origin/method/headers ------ |
  |                                            |
  | -- POST /echo + Origin + 可用凭据 ---------> |
  | <--- 200 + CORS 响应头 + 正文 -------------- |
  | 浏览器检查许可后才交给页面 JS                |
```

OPTIONS 是浏览器自动生成的权限询问，不是业务 POST 的重复执行。
规范中的 CORS 预检不携带 Cookie 等凭据，因此不能要求预检先通过登录 Cookie 验证。
实际业务请求仍必须独立鉴权；企业客户端证书场景存在实现差异，应单独测试。

Access-Control-Max-Age 缓存的是预检许可，不是接口正文，且受浏览器内部上限限制。
改了 CORS 配置却立即复测不生效时，要考虑已有预检缓存。

### credentials 与 Cookie 的三道门

fetch 默认 `credentials: 'same-origin'`；跨源携带浏览器管理的凭据需要 `include`。
但 `include` 不会越过 Cookie 的 Domain、Path、Secure、SameSite 和第三方 Cookie 策略。
跨站 Cookie 常需 SameSite=None; Secure，但即使如此，也不保证所有浏览器允许第三方 Cookie。

凭据模式为 include 时，响应必须满足：

```http
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Credentials: true
Vary: Origin
```

Allow-Origin 必须是匹配的单个源，不能使用星号或逗号拼接多个源。
不要无条件反射任意 Origin；必须先对完整来源做白名单校验。
凭据请求的 Allow-Methods、Allow-Headers、Expose-Headers 也应明确列出，不依赖星号。

Access-Control-Expose-Headers 只控制脚本能额外读取哪些响应头。
Set-Cookie 是禁止暴露给脚本的响应头，不能靠 Expose-Headers 读出；HttpOnly Cookie 也不能通过 document.cookie 读取。

### 代理与其他方案的适用边界

```text
浏览器 -- 同源 /api --> 自己的 BFF -- 服务端请求 --> 固定上游 API
           无跨源读取限制            仍需要鉴权与授权
```

代理改变的是浏览器所见的源，不是“关闭安全策略”。
代理必须限制目标、方法、请求大小和超时，不能接受任意 URL 变成开放代理或 SSRF 入口。
开发服务器的 proxy 配置不会自动进入生产部署，线上要配置真实反向代理或 BFF。

JSONP 依赖执行跨源脚本，不能作为现代敏感接口的通用方案。
postMessage 用于窗口通信，应验证 event.origin、event.source 和消息结构，不是让任意 fetch 绕过 CORS。
规则依据见 [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) 与 [Fetch Standard](https://fetch.spec.whatwg.org/#http-cors-protocol)。

## 四、代码实现

### 一个文件完成预检与凭据实验

保存为 `cors-demo.cjs`，使用 Node.js 22+，不需要第三方依赖。
默认执行 `node cors-demo.cjs` 只运行内存断言，不监听端口。
需要浏览器实验时，在独立实验目录运行 `DEMO_LISTEN=1 node cors-demo.cjs`，打开 `http://127.0.0.1:8080`。
不要换成 localhost，两者不是相同主机；实验 Cookie 不是真实登录凭据。

```js
const assert = require('node:assert/strict');
const http = require('node:http');
const allowedOrigin = 'http://127.0.0.1:8080';

function cors(origin, method, requestedMethod, requestedHeaders = '') {
  const headers = {
    Vary: 'Origin',
    'Cache-Control': 'no-store',
  };
  if (origin && origin !== allowedOrigin) return { status: 403, headers };
  if (origin) {
    headers['Access-Control-Allow-Origin'] = origin;
    headers['Access-Control-Allow-Credentials'] = 'true';
    headers['Access-Control-Expose-Headers'] = 'X-Demo';
  }
  if (method !== 'OPTIONS') return { status: 200, headers };
  headers.Vary =
    'Origin, Access-Control-Request-Method, Access-Control-Request-Headers';
  const names = requestedHeaders
    .toLowerCase()
    .split(',')
    .map((x) => x.trim())
    .filter(Boolean);
  const permitted =
    origin === allowedOrigin &&
    requestedMethod === 'POST' &&
    names.every((name) => ['content-type', 'x-demo'].includes(name));
  if (!permitted) return { status: 403, headers };
  return {
    status: 204,
    headers: {
      ...headers,
      'Access-Control-Allow-Methods': 'POST',
      'Access-Control-Allow-Headers': 'Content-Type, X-Demo',
      'Access-Control-Max-Age': '60',
    },
  };
}

assert.equal(
  cors(allowedOrigin, 'OPTIONS', 'POST', 'content-type,x-demo').status,
  204,
);
assert.equal(cors('https://evil.test', 'OPTIONS', 'POST').status, 403);
assert.equal(cors(allowedOrigin, 'OPTIONS', 'DELETE').status, 403);
assert.equal(cors(allowedOrigin, 'OPTIONS', 'POST', 'x-admin').status, 403);
assert.equal(
  cors(allowedOrigin, 'POST').headers['Access-Control-Allow-Credentials'],
  'true',
);
console.log('CORS policy: 5 cases passed');

if (process.env.DEMO_LISTEN === '1') {
  const api = http.createServer(async (req, res) => {
    const policy = cors(
      req.headers.origin,
      req.method,
      req.headers['access-control-request-method'],
      req.headers['access-control-request-headers'],
    );
    res.writeHead(policy.status, {
      ...policy.headers,
      'Content-Type': 'application/json',
      'X-Demo': 'visible',
    });
    if (policy.status !== 200) return res.end();
    // 本地无副作用回显；不依赖请求体内容，也不把 Cookie 当作认证。
    req.resume();
    res.end(JSON.stringify({ cookieSeen: Boolean(req.headers.cookie) }));
  });

  const page = `<!doctype html><meta charset="utf-8">
    <title>CORS lab</title><button id="cross">跨源请求</button>
    <button id="proxy">同源代理</button><pre id="out"></pre>
    <script>
    async function run(url) {
      try {
        const r = await fetch(url, {
          method: 'POST', credentials: 'include',
          headers: {'Content-Type': 'application/json', 'X-Demo': '1'},
          body: JSON.stringify({message: 'hello'})
        });
        document.getElementById('out').textContent =
          r.status + ' X-Demo=' + r.headers.get('X-Demo') + ' ' + await r.text();
      } catch (error) { document.getElementById('out').textContent = String(error); }
    }
    document.getElementById('cross').onclick = () => run('http://127.0.0.1:8081/echo');
    document.getElementById('proxy').onclick = () => run('/api');
    </script>`;

  const app = http.createServer(async (req, res) => {
    req.resume();
    if (req.url === '/api' && req.method === 'POST') {
      try {
        // 固定目标且不透传 Cookie：演示代理，不是通用鉴权网关。
        const upstream = await fetch('http://127.0.0.1:8081/echo', {
          method: 'POST',
          signal: AbortSignal.timeout(3000),
        });
        res.writeHead(upstream.status, {
          'Content-Type': 'application/json',
          'Cache-Control': 'no-store',
          'X-Demo': upstream.headers.get('X-Demo') ?? '',
        });
        return res.end(await upstream.text());
      } catch {
        res.writeHead(502, { 'Cache-Control': 'no-store' });
        return res.end('Upstream unavailable');
      }
    }
    res.writeHead(200, {
      'Content-Type': 'text/html; charset=utf-8',
      'Cache-Control': 'no-store',
      // Cookie 不按端口隔离；这里只为本地同站跨源实验设置。
      'Set-Cookie': 'demo=1; HttpOnly; SameSite=Lax; Path=/',
    });
    res.end(page);
  });
  api.listen(8081, '127.0.0.1');
  app.listen(8080, '127.0.0.1');
  process.on('SIGINT', () => {
    app.close();
    api.close();
  });
}
```

跨源按钮应产生 OPTIONS 与 POST；短时间再次点击可能复用预检许可。
Cookie 由 8080 页面设置，端口不隔离 Cookie，因此 include 模式的 8081 请求可见它。
同源代理按钮不产生 CORS 预检，且本例刻意不转发 Cookie，所以回显为 false。
实验仅绑定回环地址，HTTP Cookie 没有 Secure；生产登录 Cookie 应使用 HTTPS 与合适的安全属性。
本例不覆盖第三方 Cookie，因为两个端口仍然同站，也没有实现真实业务鉴权和通用正文代理。

## 五、工程实践

### 分开检查 OPTIONS 与实际请求

1. 若 OPTIONS 返回 401，检查是否被登录中间件拦截；预检只校验来源、方法和头部许可。
2. 若 OPTIONS 成功但 POST 不可读，检查实际响应是否也带有正确 CORS 头。
3. 若 200 正常、500 却变成 CORS 错误，检查错误响应路径和网关是否漏加许可头。
4. 若 Cookie 缺失，查看浏览器 Cookie 拒绝原因，而不只是反复添加 credentials。
5. 若自定义响应头为 null，检查 Expose-Headers，不把它误判成服务器没发送。
6. 若仅 CDN 路径失败，检查 Vary、重复 Allow-Origin 头与缓存污染。

调试时保留 Network 日志，确认是否出现重定向、预检缓存或不同的最终 URL。
预检允许只是浏览器放行条件，不能代替对实际 POST 的身份认证和业务授权。

### 常见误区

- **加 mode: no-cors 就能读跨域 JSON**：它通常得到不可读取正文与状态的 opaque 响应。
- **凭据请求允许星号更方便**：浏览器不会接受这种 Allow-Origin 配置。
- **CORS 能防止所有 CSRF**：免预检请求仍可能产生副作用，需要额外 CSRF 防护。
- **浏览器报错说明后端没处理**：请求可能已经执行，只是响应被阻止读取。
- **白名单匹配域名后缀就够了**：应比较完整 origin，避免把恶意相似域名放行。

## 六、总结

跨域排障要把发送、凭据与读取三层分开，并同时检查预检和实际响应。
选择同源 BFF 可以简化浏览器侧集成，但不会免除服务端安全责任。
