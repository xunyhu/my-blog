# 前端性能优化

## 一、是什么

前端性能优化是缩短用户等待、减少交互阻塞、保持布局稳定的工程过程，不是给配置文件堆开关。
有效闭环是：建立基线 → 找到瓶颈 → 实施单一假设 → 在相同条件下复测 → 观察真实访问分布。

截至本文更新日，Core Web Vitals 的三项核心指标是 LCP、INP、CLS。
[INP 已于 2024 年 3 月 12 日替代 FID](https://web.dev/blog/inp-cwv-launch)，不要继续把 FID 当作当前验收项。

| 指标                  | 用户感受           | 良好       | 需要改进            | 较差       |
| --------------------- | ------------------ | ---------- | ------------------- | ---------- |
| LCP，最大内容绘制     | 主要内容何时可见   | ≤ 2.5 秒   | > 2.5 且 ≤ 4 秒     | > 4 秒     |
| INP，交互到下一次绘制 | 操作后多久看到反馈 | ≤ 200 毫秒 | > 200 且 ≤ 500 毫秒 | > 500 毫秒 |
| CLS，累积布局偏移     | 页面是否意外跳动   | ≤ 0.1      | > 0.1 且 ≤ 0.25     | > 0.25     |

阈值分别依据 [LCP](https://web.dev/articles/lcp)、[INP](https://web.dev/articles/inp)、[CLS](https://web.dev/articles/cls) 官方定义。
CLS 没有时间单位，不能把 0.1 写成 100 毫秒。

## 二、为什么

单次 Lighthouse 高分不意味着真实用户体验良好。
实验室测试控制设备和网络，适合定位与回归；真实用户监测 RUM 覆盖不同设备、网络、缓存与实际操作。

| 数据来源                    | 擅长回答                   | 不能独自证明                 |
| --------------------------- | -------------------------- | ---------------------------- |
| DevTools Performance        | 哪个任务、资源或布局阶段慢 | 所有用户都受到同样影响       |
| Lighthouse 等实验室测试     | 固定条件下是否出现回归     | 真实访问的 INP 分布          |
| 自建 RUM                    | 哪些版本、页面群体体验差   | 自动解释所有根因             |
| Chrome UX Report 等现场数据 | 符合采集条件的真实访问分布 | 发布后立刻获得细粒度业务归因 |

CWV 通常看真实访问的第 75 百分位，也就是 p75，并分别关注移动端与桌面端。
三项各自达标才构成该组数据的整体达标，不能把它们平均成一个时间。
[阈值设计说明](https://web.dev/articles/defining-core-web-vitals-thresholds)解释了为什么选择这一分位。

平均值容易掩盖长尾，少量样本的 p75 也不稳定。
报告必须附样本数、日期窗口、设备分组、页面模板与发布版本，不能把缓存全热的开发机和低端移动端混比。

## 三、核心原理

### LCP 是关键路径，不只是图片体积

LCP 跟踪视口内符合条件的最大内容元素，其候选会随加载过程变化。
它不是所有资源加载完毕的时间，也不是随意选择一个 DOM 元素的出现时间。

```text
图片型 LCP 的典型路径
导航起点
  |--- 首字节等待 TTFB ---|
                          |--- 资源加载延迟 ---|
                                               |--- 图片下载 ---|
                                                                 |--- 渲染延迟 ---|
                                                                                   LCP
```

首字节等待高，应先查重定向、CDN 命中和源站排队。
资源很晚才开始下载，应查是否藏在 CSS、客户端数据请求之后，或被错误设置为懒加载。
图片已下载但仍未显示，则要查主线程、样式、字体、可见性与渲染机会。

首屏关键图片一般不应使用 loading="lazy"；必要时给准确的关键资源设置 fetchpriority="high"。
preload 必须匹配实际资源与请求属性，乱预加载可能重复下载或挤占真正关键资源。
优化方法与四阶段拆解见 [Optimize LCP](https://web.dev/articles/optimize-lcp)。

### INP 覆盖交互生命周期

INP 关注点击、轻触和键盘等合格交互，从输入发生到下一次绘制的延迟。
一次交互可能涉及多个事件，不等于某一个 click 回调的执行时间。

```text
用户输入
   |--- 输入延迟 ---|--- 事件处理 ---|--- 呈现延迟 ---| 下一帧
       等主线程空闲     JS 回调工作      样式、布局、绘制
   <-------------------- 交互延迟 ------------------->
```

页面没有合格交互时可能没有 INP 值，不应补成零。
算法从整个访问的交互中选取接近最差的代表值，在大量交互时排除部分极端异常值；它不是所有事件 duration 的简单平均或最大值。
正式采集应使用处理这些边界的库，而不是手写一个 PerformanceObserver 就宣称复刻了 INP。

减少 JS 体积有帮助，但首次加载后第三方脚本、同步计算、巨大 DOM 更新也会阻塞交互。
可将纯计算移到 Worker，或把非紧急工作切成多个任务；Worker 不能直接操作 DOM。
Promise 微任务不会自动让浏览器绘制，把长循环包进 async 函数也不等于让出主线程。

### CLS 是最大会话窗口

布局偏移分数考虑受影响的视口比例与移动距离，不是统计 DOM 改动次数。
普通连续交互引发的滚动与真正意外的布局位移也不能混为一谈。

```text
时间线:   偏移 A  偏移 B          偏移 C  偏移 D
           |------|               |------|
窗口一:      得分 0.04
窗口二:                            得分 0.12
CLS = max(0.04, 0.12) = 0.12，而不是 0.16
```

窗口内相邻偏移间隔小于 1 秒，整个窗口最长 5 秒；取最大窗口的累计分数。
这一规则见 [CLS 窗口更新说明](https://web.dev/blog/cls-web-tooling)，不应无限累加整次访问的所有偏移。
符合条件的近期用户输入后的偏移会被排除，但不能因此忽略较晚异步插入内容带来的跳动。

给图片设置尺寸或 aspect-ratio，为广告和异步组件预留位置，比偏移后再修补布局更可靠。
字体替换也可能改变文字几何尺寸；动画优先考虑不影响文档流的属性，但 transform 并非零成本保证。

## 四、代码实现

### 在真实浏览器中测量，而不是编造分数

保存以下完整页面为 `vitals-lab.html`，用现代 Chromium 浏览器打开，DevTools Console 开启 Preserve log。
不需要本地服务或业务 API；唯一外部依赖是从 CDN 加载的 [GoogleChrome/web-vitals](https://github.com/GoogleChrome/web-vitals) 5.x 模块。
需能访问 unpkg.com；CDN 故障、离线或 CSP 拦截会导致采集失败，页面会显示错误，不会用零值冒充成功。
生产应通过构建安装并锁定已审查的具体版本、自托管资源；这里的主版本 URL 仅用于独立实验。

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Core Web Vitals lab</title>
    <style>
      body {
        max-width: 50rem;
        margin: 2rem auto;
        padding: 1rem;
        font-family: sans-serif;
      }
      h1 {
        font-size: 3rem;
      }
      #slot {
        background: #e2e8f0;
      }
      #notice {
        position: fixed;
        bottom: 0;
        left: 0;
        margin: 0;
        background: white;
      }
    </style>
  </head>
  <body>
    <div id="slot"></div>
    <h1>观察加载、交互和布局稳定性</h1>
    <p>等待三秒，再点击按钮，切换到其他标签页后返回，查看控制台。</p>
    <button id="work" disabled>执行一次交互</button>
    <p id="notice">正在加载测量模块</p>
    <script type="module">
      const faulty = location.hash === '#faults';
      const slot = document.getElementById('slot');
      const button = document.getElementById('work');
      const notice = document.getElementById('notice');
      // 默认预留空间；#faults 模式故意不预留，用来对比布局偏移。
      if (!faulty) slot.style.minHeight = '120px';
      const latest = new Map();
      function record({ name, id, value, delta, rating, navigationType }) {
        const key = `${name}:${id}`;
        const previous = latest.get(key);
        const row = {
          name,
          id,
          value,
          delta,
          rating,
          navigationType,
          sequence: (previous?.sequence ?? 0) + 1,
        };
        latest.set(key, row);
        if (latest.size > 100) latest.delete(latest.keys().next().value);
        console.log('CWV observation', JSON.stringify(row));
      }
      try {
        const { onLCP, onINP, onCLS } =
          await import('https://unpkg.com/web-vitals@5?module');
        // 每种指标仅注册一次；调试时观察变化，生产默认不必逐次上报。
        onLCP(record, { reportAllChanges: true });
        onINP(record, { reportAllChanges: true });
        onCLS(record, { reportAllChanges: true });
        notice.textContent = faulty
          ? '故障模式：不预留空间、同步阻塞'
          : '基线模式';
        button.disabled = false;
        setTimeout(() => {
          slot.style.height = '120px';
          slot.textContent = '模拟异步到达的内容';
        }, 2000);
        button.onclick = () => {
          if (faulty) {
            const end = performance.now() + 600;
            while (performance.now() < end) {
              /* 只用于演示阻塞，禁止复制到生产。 */
            }
          }
          button.textContent = '已响应';
        };
      } catch (error) {
        notice.textContent = `测量未启动：${String(error)}`;
      }
    </script>
  </body>
</html>
```

先测基线，再把地址改为 `vitals-lab.html#faults` 并完整刷新；只修改 hash 不会重新执行初始化代码。
两次都在前台加载，等待内容出现，再实际点击按钮并切换标签页。
不要用脚本合成 click 替代真实输入，也不要一边滚动一边比较 LCP。

应观察故障模式中同步任务拉长交互，未预留空间可能增加 CLS；具体数值依赖视口、时机和设备，不预设固定结果。
回调可能在交互、页面隐藏时才报告；没有 INP 或后台加载时没有某些指标，不等于采集值为零。
reportAllChanges 报告指标变化，不保证每一个输入事件或布局偏移都触发回调。

本例输出的是当前实验页面的实际观测，不代表博客站点或全体用户的数据。
接入真实站点时应在页面生命周期早期注册，保留必要的采集许可与采样策略；临时在 Console 注入可能遗漏早期条目。
模块已处理 bfcache 等生命周期；不要在每次组件渲染、客户端切路由时重复注册。
软导航的支持取决于浏览器与库版本，必须单独验证，不能把普通硬导航指标随意归给每个路由。

### 离线验证去重与第 75 百分位

同一个 metric id 可以多次报告；不能把每次报告都当成一次新访问，也不能累加 value。
若采用 value 覆盖方案，应使用采集序号拒绝乱序旧消息；delta 求和是另一种方案，还需要传输去重。
bfcache 恢复会产生新的指标 ID，不要只按 URL 把整天所有访问合并成一条。

以下保存为 `vitals-aggregate.cjs`，用 Node.js 22+ 执行，无第三方依赖、网络或写入。
样本是明确标注的合成数据，只检验聚合算法，不是本站的 RUM 结果。

```js
const assert = require('node:assert/strict');
const names = new Set(['LCP', 'INP', 'CLS']);

function aggregate(reports, name) {
  const latest = new Map();
  for (const row of reports) {
    if (
      !names.has(row.name) ||
      typeof row.id !== 'string' ||
      !row.id ||
      !Number.isFinite(row.value) ||
      row.value < 0 ||
      !Number.isInteger(row.sequence) ||
      row.sequence < 1
    )
      continue;
    const key = `${row.name}:${row.id}`;
    if (!latest.has(key) || row.sequence > latest.get(key).sequence) {
      latest.set(key, row);
    }
  }
  const values = [...latest.values()]
    .filter((row) => row.name === name)
    .map((row) => row.value)
    .sort((a, b) => a - b);
  return {
    count: values.length,
    p75: values.length ? values[Math.ceil(values.length * 0.75) - 1] : null,
  };
}

const rows = [
  { name: 'LCP', id: 'a', sequence: 1, value: 1000 },
  { name: 'LCP', id: 'a', sequence: 2, value: 2000 },
  { name: 'LCP', id: 'a', sequence: 1, value: 1000 }, // 乱序旧报告
  { name: 'LCP', id: 'b', sequence: 1, value: 2400 },
  { name: 'LCP', id: 'c', sequence: 1, value: 3000 },
  { name: 'LCP', id: 'd', sequence: 1, value: 5000 },
  { name: 'LCP', id: 'bad', sequence: 1, value: NaN },
  { name: 'CLS', id: 'a', sequence: 1, value: 0.05 },
];
assert.deepEqual(aggregate(rows, 'LCP'), { count: 4, p75: 3000 });
assert.deepEqual(aggregate([...rows, ...rows], 'LCP'), { count: 4, p75: 3000 });
assert.deepEqual(aggregate(rows, 'CLS'), { count: 1, p75: 0.05 });
assert.deepEqual(aggregate(rows, 'INP'), { count: 0, p75: null });
console.log('Deduplication, ordering, metric isolation and p75: passed');
```

这里选择 nearest-rank 分位算法，小样本与分析平台的插值算法可能得到不同结果，应明确口径。
生产先按页面模板、设备档位、版本与日期窗口分组，再聚合该组访问，不跨指标混合单位。
服务端还要校验请求结构、大小、时间范围与采集序号；这些样本校验不能替代完整接收端。

## 五、工程实践

### 从证据决定改哪里

| 现象                   | 需要的证据                      | 优先改动                          | 复测防线               |
| ---------------------- | ------------------------------- | --------------------------------- | ---------------------- |
| LCP 的 TTFB 高         | 导航瀑布、CDN 命中、服务端追踪  | 缩短跳转、优化回源与缓存          | 不把个性化内容公开缓存 |
| LCP 图片发现晚         | Initiator、优先级、请求开始时间 | HTML 直出关键引用，去除错误懒加载 | 不预加载整页资源       |
| 图片下载完却迟迟不可见 | LCP 分段、主线程轨迹            | 减少阻塞脚本、渲染等待            | 不只比较压缩后字节数   |
| INP 输入延迟长         | 交互前的长任务                  | 减少第三方同步工作、切分计算      | 弱设备也能及时响应     |
| INP 呈现延迟长         | 样式、布局、绘制阶段            | 减少 DOM、批量读写、按需渲染      | 同时检查 CLS           |
| CLS 上升               | Layout shifts 轨迹、偏移元素    | 预留尺寸、稳定字体与异步容器      | 整个会话而非只测首屏   |

一次只改变主要变量，保存优化前后相同条件的 trace，再观察足够样本的现场 p75。
TBT 等实验室指标可辅助发现主线程阻塞，但不是 INP 的替代统计。
代码分割、压缩、HTTP/3、CDN、Worker 都是工具，不是无条件的优化结论。

### 建立可用且克制的 RUM

1. 为指标保留 name、id、value、sequence、导航类型、发布版本和经脱敏的页面模板。
2. 不上传 DOM 文本、Cookie、用户输入或完整查询串；attribution 数据也要裁剪和脱敏。
3. 明确采样比例与未采集原因，记录样本数；不支持的指标保留缺失状态。
4. 发送端可使用受限大小的 sendBeacon 或 keepalive 请求，但不要假设离页上报百分之百成功。
5. 接收端按 ID 与序号幂等更新，限制存储窗口与高基数字段，避免监测系统成为新的负担。
6. 优化上线后观察回归与业务完成时间，既不能只看分数，也不能把加载快当作业务成功。

本文不提供虚构的 `/api/metrics` 接口，也不会声称上述控制台实验已经替代了生产采集链路。
需要根因信息时，可评估库的 attribution 构建，先确认额外数据、体积与隐私成本。

### 常见误区

- **仍以 FID 作为 CWV 验收**：当前交互项是 INP，而且覆盖的不只是首次输入。
- **平均 LCP 达标就算通过**：应使用明确人群与窗口的分位数据，附样本量。
- **CLS 是所有偏移无限累加**：应按最大会话窗口与排除规则计算。
- **一条 event.duration 就是 INP**：需要交互分组、生命周期与异常值处理。
- **没有回调就补零**：可能是无交互、后台加载、API 不支持或采集失败。
- **所有图片都懒加载更快**：可能直接推迟首屏 LCP 资源。
- **改成微任务就不阻塞**：微任务仍在主线程执行，连续队列也会推迟绘制。

## 六、总结

用 LCP、INP、CLS 分别约束主要内容可见、交互反馈与视觉稳定性。
用实验室轨迹解释原因，用真实访问分布验证收益；任何性能结论都应附带条件、样本与证据。
